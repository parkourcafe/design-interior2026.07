# AP5 Runbook — authenticated browser matrix

Гейт AP5 из `docs/product-intelligence/wave-3/MASTER_EXECUTION_PLAN.md` §AP5:
одна Organization проходит цепочку Kora, **browser matrix выполняется отдельной
authenticated session для каждой роли**. Переключение роли через query, фикстуру
или клиентское состояние доказательством не считается.

Этот документ описывает, что прогон делает, что он доказывает и что он ещё **не**
доказывает. Читать вместе с `AP1_RUNBOOK.md` §5: санитизированный харнесс
`/projectceo-qa/[role]` и настоящая Auth/PostgREST/RLS-матрица — разные вещи, и
первое второе не заменяет.

## Где он живёт

Job `ap5` в `.github/workflows/ci.yml`. Не в каждом push — поднимает весь стек
Supabase и идёт ~15 минут:

- вручную — **Actions → CI → Run workflow**;
- на PR — повесить метку `ap5`.

**Job блокирующий — но зелёный job НЕ означает «AP5 закрыт».** Это разные вещи,
и путать их опасно:

- **job как регрессионный гейт** — блокирующий. Он падает, когда ломается путь,
  который сегодня работает. Первым же прогоном он нашёл два настоящих дефекта
  (см. «Что гейт уже нашёл»), и держать его информационным дальше значило бы
  заранее согласиться, что следующую находку никто не заметит;
- **AP5 как ворота приёмки** из `MASTER_EXECUTION_PLAN` — **не закрыт.** Он
  закрывается тогда, когда в спеке не останется ни одного `test.fixme`, то есть
  когда вся цепочка Kora пройдена браузером. Сегодня их два: 12.08.2026
  влияние изменения закрылось целиком — системный расчёт И рассмотрение
  архитектором (V1 Impact, шаги 5б и 12).

Звенья, требующие воркерного расчёта, помечены `test.fixme` с причиной (см.
«Чего он не доказывает») — они видны в отчёте как пропуски и прогон не роняют.
Поэтому зелёный прогон читается как «ничего из работающего не сломано», а не
как «ворота пройдены».

## Что делает прогон

1. `supabase start` из репозиторного `supabase/config.toml`: порты, список схем
   в Data API и `custom_access_token` hook берутся оттуда, а не из дефолтов CLI.
2. `tests/ap1/environment/verify-db.sql` — состояние базы: managed-auth ссылок не
   осталось, request-claim helpers на месте, приватные гранты закрыты.
3. `tests/ap1/environment/verify-runtime.mjs` — разрешённые схемы отвечают,
   приватные закрыты `406`, Auth и Storage живы.
4. `npm run provision:ap1` — пять auth-identity. **Только identity.** Членства
   скрипт не выдаёт: human operations через service role запрещены.
5. Сборка и запуск приложения на `http://127.0.0.1:3100` (этот адрес есть в
   `additional_redirect_urls`, другой Auth не примет).
6. `npm run test:ap5` — Playwright.

## Что доказывает прогон

`tests/ap5/global-setup.ts`:

- **живой стек, а не фикстуры.** Портфель без сессии обязан ответить `401`.
  Мок-порт ответил бы данными, и вся матрица стала бы бессмысленной. Плюс
  прямой запрет `PROJECTCEO_LOCAL_FIXTURE_MODE=1`;
- **пять отдельных сессий,** каждая рождается в браузере: он сам проходит по
  одноразовой ссылке через `/auth/callback` и получает куку, ничего не
  подкладывается в контекст.

  Вход именно по ссылке, а не по паролю, — требование контракта, а не удобство.
  `public.projectceo_custom_access_token_hook` (миграции `20260801150000` и
  `20260802001000`) выдаёт claim `email_verified` только методам, доказывающим
  владение адресом: `otp`, `magiclink`, `invite`, `email/signup`. Вход по паролю
  его не получает намеренно, и вся поверхность ProjectCEO для такой сессии
  закрыта как `identity_unverified`. Первый прогон матрицы на этом и
  остановился — на приёме приглашения.

  Ящика в стенде нет (`local_smtp` выключен), поэтому письмо заменяется выпуском
  ссылки через admin API. Service role здесь подменяет **доставку письма**, а не
  выполняет операцию за человека;
- **приглашения** выпускает owner своей сессией (`create_invitation` →
  `invitationUrl`), а принимает каждый приглашённый — своей, на реальной
  странице `/projectceo/invitations/[token]`.

`01-authenticated-role-matrix.spec.ts`:

| Проверка | Что доказывает |
|---|---|
| портфель без сессии → 401 | стек живой |
| каждая роль открывает `/dashboard/projectceo` и страницу проекта | серверный рендер под своей сессией |
| `actor.role` в проекции равен роли членства | роль считается от членства |
| роль в query и заголовке игнорируется | подмена роли клиентом невозможна |
| guest без членства → 404 | deny-by-default у настоящей сессии |
| чужой projectId → 403/404 | изоляция арендатора |
| мутация с чужим Origin → 403 | same-origin у команд |

`02-kora-chain.spec.ts` — звенья цепочки, достижимые сегодня: регистрация
проекта, приём приглашений тремя ролями, регистрация санитизированного
источника, честный отказ в ревью до воркерного ingest, решение человеческого
происхождения, публикация baseline и выпуск производственной версии (гейт 1),
выдача, подтверждение получения сессией получателя и заявка на изменение
(гейт 2). Плюс отдельная проверка, что закрытое названо своей причиной:
неавторизованные команды отдаются как `increment_not_authorized`, а не
имитируются браузером.

**Влияние изменения — с 12.08.2026 целиком (V1 Impact).** Шаг 5б добавляет в
граф узел, зависящий от решения (одно обратное ребро
`spec --depends_on--> decision`); шаг 11 создаёт заявку браузером; шаг 12
запускает настоящий воркер `npm run worker:change-impact`, который сам находит
очередь и даёт непустой прогон; архитектор рассматривает карточку своей
браузерной сессией через публичный маршрут команд, и результат возвращается
клиенту. Там же проверяются отказы: повторное решение по той же карточке и
подтверждение неполноты полного прогона отклоняются, а состояние не меняется.

Рёбра графа пишет единственная функция `ingest_source_graph`, HTTP-двери у неё
нет, поэтому шаг 5б идёт RPC — но ТОКЕНОМ архитектора: функция выдана
`authenticated` и отозвана у `service_role` (`20260717092000`), системная
identity её выполнить не может.

**Авторизация и оба состояния неполноты — с 12.08.2026 (OWNER REVIEW, поверх
DEC-034/035/036).** Шаг 12 доказывает `complete` и человеческую поверхность
рассмотрения; шаги 13–15 закрывают три оставшихся требования тем же
стандартом (настоящая страница, а не только JSON команд):

- **Шаг 13** — три системные двери расчёта (`calculate_change_impact`,
  `calculate_change_impact_policy_bound`, `list_change_impact_backlog`)
  недостижимы ОТДЕЛЬНОЙ аутентифицированной сессией архитектора через
  настоящий Data API (PostgREST), в обход приложения. Аргументы намеренно
  негодные — отказ обязан прийти по правам, до тела функции: `401`/`403`/`404`
  допустимы, `400` нет (он значил бы, что роль эту RPC вообще видит).
- **Шаг 14** — `partial_depth` на настоящей странице. Глубокая цепочка узлов
  (`ingestDepthChain`, глубже текущей политики) даёт обход, который система
  не проходит целиком. Настоящий воркер считает, архитектор своей браузерной
  сессией открывает `/dashboard/projectceo/projects/[id]`, видит дословный
  текст «Показаны найденные влияния. Анализ ограничен глубиной и не является
  полным», рассматривает ВСЕ показанные карточки настоящими кликами — и DOM
  всё равно показывает «Рассмотрение не закрыто»: рассмотреть всё показанное
  не значит закрыть анализ. Ни одной кнопки человеческого override нигде на
  странице — она не существует, а не просто задизейблена.
- **Шаг 15** — `blocked_result_limit` на настоящей странице. Широкая звезда
  узлов (`ingestWideStar`, заведомо больше `maxImpacts`) даёт обход, который
  упирается в лимит результата раньше глубины. Текст блокировки виден
  дословно, весь блок с кнопками рассмотрения не рендерится ВООБЩЕ (не
  «недоступно» — рассматривать нечего, `impactCount = 0`), и повторный проход
  настоящего воркера подтверждает: заявка исчезла из активной очереди совсем.

Фикстуры шагов 14/15 (глубокая цепочка, широкая звезда) собирает та же RPC,
что и шаг 5б (`ingest_source_graph`, токен архитектора, не service role) —
единственная дверь, которая пишет рёбра графа. Расчёт и рассмотрение по-прежнему
идут настоящей системной RPC и настоящей браузерной сессией; фикстурой
собирается только предметная область.

## Чего он не доказывает

Это не оговорки на будущее, а текущее состояние продукта. Каждое — причина, по
которой AP5 сегодня не закрыт.

1. **Привязка проекта к ProjectCEO не проходит через браузер.**
   Сам проект создаётся штатно и в браузере — формой дизайнера на
   `/dashboard`; `enroll_organization_project` его не создаёт, а берёт
   существующую строку `public.projects` и требует совпадения `designer_id` с
   актором. А вот у самой этой RPC нет ни HTTP-маршрута, ни элемента
   интерфейса: `FoundationService`
   (`lib/project-intelligence/delivery/server/foundation-service.ts`) не
   подключён никуда. В прогоне вызов идёт RPC от лица owner **его же** access
   token — инвариант про service role соблюдён, но браузерным доказательством
   этот шаг не является. Чтобы закрыть: маршрут привязки плюс экран, после
   этого убрать обход из `global-setup.ts`.
2. **Артефакт выпуска собирает система, а не браузер.** Гейт 1 и гейт 2
   пройдены целиком (звенья 6, 7 и 9–11), но между выпуском и выдачей стоит шаг,
   человеку недоступный по замыслу: сборка артефакта
   (`build_release_artifact`, только `service_role`). С 11.08 его делает
   настоящий воркер (DEC-030), а не psql-мост, — см. «Дефект 5». Чем запускать
   воркер в продакшене (cron, очередь, вызов после публикации) — отдельное
   решение вместе с production-включением M4.
3. **Фотодоказательство и приёмка вехи.** `upload_photo_evidence` требует
   существующего `milestoneId`; вех без воркерного плана в проекте нет.
4. **Граф утверждений.** Из браузера проходит только `claimStatus:
   "human_origin"` с пустым `evidence`: ссылки на evidence рождаются в
   `ingest_source_graph` (`command-contract.ts`).
5. **Выбор привязан к площади.** У решения `areaNodeId` допускает null — и
   решение из браузера создаётся. У выбора он обязателен и должен ссылаться на
   существующий узел `kind='area'` в `project_intelligence.graph_nodes`; такие
   узлы создаёт ingest, а RPC решения заводит узел только для собственного
   `nodeId` (`20260717101000:661`). Выдуманный идентификатор отвергается как
   `AREA_NODE_INVALID` (там же, строка 679).

Влияния изменения в этом списке БОЛЬШЕ НЕТ: с 12.08.2026 звено доказано целиком
(см. «Что доказывает прогон»). Оставлять его здесь значило бы держать в отчёте
противоречие — «последний гейт закрыт» рядом с «не доказано».

Всё остальное перечислено в спеке как `test.fixme` с причиной — пропуск виден в
отчёте, а не растворяется в зелёном.

## Что гейт уже нашёл и что из этого починено

Два дефекта, лежавших друг на друге: первый маскировал второй. Порядок здесь
не хронология, а причинно-следственная связь — второй стал виден только после
починки первого.

**Дефект 1. Ревью источника отвечало 500 — исправлено.** Решение по источнику пишет
`project_intelligence_api.review_claim`, а эта схема намеренно **не отдана Data
API** (`supabase/config.toml`; `verify-runtime.mjs` требует от неё `406`).
PostgREST такой вызов не находил, ошибка не ложилась ни на один SQLSTATE и
выходила наружу как **500 `internal_error`** — при том что поверхность действие
**предлагала**. Проверено на живом PostgreSQL: сама RPC отвечает корректно
(`P1006 STATE_STALE` на устаревшую ревизию состояния, `P1103 forbidden` не
члену проекта), то есть дело было не в графе утверждений, а в границе схем.

Починка — миграция `20260810050000`: тонкая делегирующая функция
`projectceo_api.review_source` в уже отданной схеме. Прав она не добавляет:
`security invoker`, а `usage` на приватную api-схему и `execute` на
`review_claim` у роли `authenticated` были и до неё — это отдельно проверяет
сценарий `tests/db4/37_source_review_door.sql`. Меняется ровно достижимость
через Data API.

Попутно закрыт второй путь к 500: повторное решение по уже отрецензированной
ревизии упиралось в `human_reviews_target_revision_key` и выходило сырым
`23505`, который `errors.ts` не отображает. Дверь переводит именно это
ограничение в `P1009` → `scope_conflict`; любое другое нарушение уникальности
пробрасывается как было.

**Дефект 2. Поверхность предлагала ревью ревизии, которой нет в графе —
исправлено.** Как только дверь убрала 500, прогон стал отвечать
**409 `stale_state`**. Это и был второй дефект, всё это время закрытый первым.

Источник, заведённый человеком, попадает в инвентарь
(`projectceo_foundation.source_inventory_records`), но узлы и ревизии графа
утверждений создаёт воркерный `ingest_source_graph` — операция, человеку
недоступная. Чтение при этом отдавало `reviewTargetRevisionId` прямо из
инвентаря (`20260718124958`), а `reviewStatus` считало `pending` просто потому,
что решения ещё нет. То есть кнопка ревью выглядела рабочей для ревизии,
которой в графе не существует.

`review_claim` отвечал на это ровно так, как должен: `P1004 REVISION_STALE`,
`currentRevisionId: null`. Воспроизведено на живом PostgreSQL по шагам
«регистрация источника → чтение → ревью»; заодно проверено и снято подозрение,
что счётчиков ревизии состояния два — `project_workflows.state_revision`,
`list_projects` и верхний уровень чтения дают одно и то же число.

Починка — чтение **v8** (`20260810060000`): `reviewTargetRevisionId`
non-null только тогда, когда ревизия действительно есть в
`project_intelligence.graph_node_revisions`. Новая версия, а не правка v7:
чтения здесь версионированный контракт, и менять поведение отданной версии
нельзя. v8 сужает ровно одно поле — состав, порядок и `stateRevision` те же,
это проверяет DB4-сценарий.

Следствие для звена 4: из браузера сегодня проверяется **не** успешное ревью, а
то, что поверхность честно говорит `prerequisite_missing`, и что команда в
обход интерфейса получает контролируемый `404 not_found`. Успешный путь
откроется вместе с воркерным ingest — до тех пор его доказывает DB4
(`tests/db4/37_source_review_door.sql`), где ревизия в графе есть.

**Дефект 3. Отказ харнесса был неотличим от отказа сервера — исправлено.**
Прогон 156 (`actions/runs/31413335001`) упал на звене 5: `create_decision`
ответил **400 `validation_failed`**, звенья 6 и 7 не запустились. Ни в логе
приложения, ни в артефакте причины не было — тело ответа несёт только код.

Причина оказалась в самом харнессе. Звено 6 одобряет ту же ревизию, что создало
звено 5, поэтому её идентификатор переехал из тела теста в общую константу — и
при переезде вместо `randomUUID()` получил читаемое значение
`"ap5-decision-revision-1"`. Контракт команды объявляет `revisionId` у
`create_decision` строго uuid (`command-contract.ts`), маршрут отверг конверт
на `safeParse` **до всякого RPC** — тем же кодом `validation_failed`, каким
отвечает и настоящий отказ базы. База приняла бы это значение (там `revisionId`
— текст до 160 символов), но команда до неё не дошла.

Проверено отдельно, чтобы не чинить не то: на живом PostgreSQL с этими же
миграциями вся SQL-цепочка звена 5 проходит от лица архитектора —
`register_source_inventory` → `get_project_delivery` →
`append_decision_revision` с `human_origin` и пустым `evidence` возвращают
`revisionNo: 1`. Дефекта сервера здесь нет.

Починка — три вещи, а не одна:
1. `AP5_DECISION_REVISION_ID` стал uuid и живёт в `tests/ap5/ap5-env.ts`
   рядом с остальными идентификаторами цепочки.
2. Хелпер `command()` в `02-kora-chain.spec.ts` прогоняет конверт через
   `projectCeoCommandSchema` перед отправкой и падает с текстом «дефект
   харнесса, не сервера» и списком нарушений. Гейт не ослаблен: контрактно
   валидные payload'ы, которыми тесты проверяют отказы сервера, уходят как
   уходили.
3. `tests/projectceo-integration/ap5-chain-identifiers.test.ts` — офлайновый
   гейт: те же идентификаторы через ту же схему, 20 миллисекунд в `npm run
   test`. Именно он ловит этот класс дефекта на push, а не сорокапятиминутный
   браузерный прогон.

**Дефект 4. Ожидание теста отстало от guardrail'а M4 — исправлено.** В том же
прогоне 159, уже после зелёного звена 6, упала проверка `build_handover`: она
ждала причину `worker_only`, а поверхность ответила `module_disabled`.

Это не регресс, а результат guardrail'а от 10.08: модуль исполнения закрыт
флагом `REMHAOS_EXECUTION_ENABLED` целиком (`execution-flag.ts` плюс миграция
`20260810070000` на второй границе), и причина `module_disabled` сильнее и
честнее прежней — закрыта не одна операция, а весь модуль, роль тут ни при чём.
Тест писался до guardrail'а и продолжал утверждать вчерашнюю правду.

Проверка переписана под сегодняшнее поведение и заодно расширена: закрытыми
обязаны быть и три команды инкремента 1 (`distribute_release`,
`acknowledge_release`, `create_change`), иначе «закрыт модуль» означало бы
«закрыта одна кнопка». Флаг в прогоне намеренно не включается — A6 §5.1 его не
разрешает, и включить его ради зелёного теста значило бы открыть поверхность
M4 без основания.

**Результат: прогон 161 (`ca597b1`) зелёный целиком** — первый зелёный
блокирующий AP5. Джобы: browser matrix ✓, `lint · typecheck · test · build` ✓,
DB4 на PG16 и PG17 ✓. Красный только цикл 7 — информационный и намеренный
(A5 §4.3). Что это доказывает и чего не доказывает — раздел «Чего он не
доказывает», пункт 2: первая половина гейта 1 взята, вторая ждёт
`publish_release`.

**Гейт 1 закрыт целиком: прогон 186 (`7c68139`)** — звено 7 (`publish_release`)
прошло живьём, включая отказ повторного выпуска устаревшим токеном. Влито в
`main` как #79.

**Дефект 5. У выдачи есть воркерная предпосылка, которой A6 не ожидал.**
Найден при постройке гейта 2 (11.08). A6 §1.1 утверждает, что у инкремента 1
воркерных предпосылок нет — «им нужен только выпущенный пакет». Для
`acknowledge_release` и `create_change` это верно. Для выдачи — нет:
`distribute_release_request_bound` ищет строку в
`projectceo_product.release_artifacts` и без неё отвечает
`P1104 not_found {"entity":"releaseArtifact"}`. Собрать артефакт может только
система: у `build_release_artifact` права есть лишь у `service_role`, а запись
помечается `created_by_id = 'system:projectceo-product-worker'`. Человеческой
двери к ней нет и по замыслу не будет.

Дефект не в коде, а в ожидании документа, поэтому «починка» здесь — назвать
факт и не изображать его отсутствие. В прогоне 195 артефакт материализовал
psql-скрипт: он доказывал поведение базы, но не существование воркера.

**Закрыто 11.08 этапом M4 Worker Foundation (DEC-030):** psql-мост удалён,
звено 9 зовёт настоящий воркер — `npm run worker:release-artifacts`. Очередь
воркер находит сам; ни версии, ни идентификатора артефакта прогон ему не
передаёт, иначе недоказанным осталось бы ровно то, ради чего он написан. Там же
проверяется повтор: второй запуск видит пустую очередь и ничего не создаёт.

**Дефект 6. Guardrail модуля 4 не закрывал модуль 4 — исправлено.** Миграция
`20260810070000` отзывала права сплошь по схеме `projectceo_m4_api` и выглядела
исчерпывающей именно потому, что была сплошной. Четыре командные RPC модуля
живут в продуктовой схеме (`distribute_release`, `acknowledge_release` и их
request-bound версии), права `authenticated` на них выданы в `20260717101000` и
`20260718124958`, и отзыв по схеме M4 их не касался: выдача выпущенного пакета
и подтверждение получения были доступны через Data API при выключенном модуле.

Закрыто `20260811020000`. Проверяется тремя способами, потому что одного мало:
`tests/db4/07_m4_execution_boundary.sql` (реальные вызовы из-под роли,
insufficient_privilege до тела функции), `tests/ap1/environment/
verify-m4-data-api-closed.mjs` (настоящий JWT, настоящий PostgREST, шаг стоит
ДО включения) и матрица `m4-surface.ts` с тестами, роняющими CI при
расхождении.

**Дефект 7. Второй baseline не публиковался вовсе — исправлено.** Прогон 193
дошёл до звена 11 и упал на `create_change` с `400 validation_failed`. Отказ
пришёл из базы: `NO_CHANGE_ROOTS`. Заявка на изменение строит корни из пар
«одна сущность, разные ревизии» между прежним и предложенным baseline, а
предложенный baseline в прогоне был побайтово равен прежнему — менять было
нечего.

Попытка сделать его отличающимся обнажила настоящий дефект, лежавший глубже.
Сборщик состава (`baseline-composition.ts`) складывал ревизии всех одобренных
approval packages в одно множество. Пока baseline в проекте один, это
незаметно. Как только решение пересматривают и одобряют заново, в состав
попадают ОБЕ ревизии одного узла — и заменённая, и новая. Такой дескриптор
`publish_project_baseline` отвергает: каждая ревизия обязана входить в
публикуемую версию графа, а версия содержит только текущие
(`BASELINE_REVISION_NOT_IN_GRAPH_VERSION`). То есть **второй baseline,
отличающийся от первого, не публиковался ни при каких действиях пользователя** —
а без него невозможен весь модуль 4, чей вход и есть расхождение редакций.

Починка — уточнение правила полноты: замораживается по одной ревизии на
сущность, побеждает ревизия из самого позднего одобрившего пакета. Это не
ослабление правила A′, а его исполнение: заморозке подлежит утверждённое
состояние, а не история утверждений. Порядок пакетов берётся из
`approval.created_at` с тай-брейком по идентификатору — состав участвует в
хеше и обязан быть детерминированным.

Звено 11 переписано под настоящий пересмотр: новая ревизия того же решения →
новый approval package → одобрение → baseline V2 → заявка от строителя. Прежняя
редакция публиковала baseline повторно без изменений и доказывала бы не то.

**Гейт 2 (`M4_INCREMENT1_BROWSER_PROVEN`) — звенья 9, 10, 11.** Выдача сессией
владельца, подтверждение получения **сессией получателя** (строителя, не
отправителя — A6 §6.1 требует именно этого), заявка на изменение от строителя
по устаревшей редакции. Флаг `REMHAOS_EXECUTION_ENABLED` в прогоне включён:
после гейта 1 A6 §6.3 разрешает интерфейс инкремента 1, а доказать его иначе,
чем при включённом модуле, нельзя. Вторая граница включается отдельным шагом
джобы и только в этом одноразовом стеке.

**Результат: прогон 195 (`7bf00fd`) зелёный целиком** — гейт 2 взят, состояние
`M4_BROWSER_PROVEN` (A6 §7) достигнуто. Джобы: AP5 ✓ (20 пройдено, 3
`test.fixme` с причинами), `lint · typecheck · test · build` ✓, DB4 на PG16 и
PG17 ✓. Красный только цикл 7 — информационный и намеренный. В той же джобе
шаги «Verify M3/M4 … closed on the Data API» стоят ДО шагов включения, то есть
default-deny доказан настоящим JWT по настоящему HTTP, а не описан.

## Локальный прогон

Нужен docker (стенд, а не этот репозиторий сам по себе):

```bash
supabase start
supabase status -o env            # взять API_URL, ANON_KEY, SERVICE_ROLE_KEY, DB_URL
# положить их в .env.local вместе с AP1_TEST_PASSWORD и PROJECTCEO_TOKEN_SECRET
AP1_CONFIRM_DISPOSABLE=yes npm run provision:ap1
# Обе границы модулей — база закрыта по умолчанию, и флаг приложения этого не
# отменяет. Проверки закрытости запускать ДО включения, иначе они мерят открытую
# базу.
node tests/ap1/environment/verify-m3-data-api-closed.mjs
node tests/ap1/environment/verify-m4-data-api-closed.mjs
psql "$SUPABASE_DB_URL" -X --set ON_ERROR_STOP=1 -f tests/ap1/environment/enable-m3-publication.sql
psql "$SUPABASE_DB_URL" -X --set ON_ERROR_STOP=1 -f tests/ap1/environment/enable-m4-increment-1.sql
REMHAOS_DOCUMENTATION_ENABLED=true REMHAOS_EXECUTION_ENABLED=true npm run build
PORT=3100 REMHAOS_DOCUMENTATION_ENABLED=true REMHAOS_EXECUTION_ENABLED=true npm run start &
npx playwright install chromium
# SUPABASE_DB_URL нужен самому прогону: звено 9 материализует артефакт выпуска
# от лица системного воркера (`tests/ap5/release-worker.ts`), человеческой двери
# к `build_release_artifact` нет.
SUPABASE_DB_URL="$SUPABASE_DB_URL" npm run test:ap5
```

`tests/ap5/.state/` — одноразовое состояние прогона: файлы сессий содержат живые
access token, каталог в `.gitignore` и коммиту не подлежит.

## Попутная находка

Схема `projectceo_m3_api` не была отдана Data API в `supabase/config.toml`, хотя
приложение вызывает её листы через PostgREST
(`lib/project-intelligence/adapters/postgres/documentation.ts`). На голом
PostgreSQL это невидимо — DB4 ходит напрямую в базу; на живом стеке RPC
документации просто не существовало бы для приложения. Схема добавлена,
приватная `projectceo_m3` остаётся закрытой, обе проверки — в
`environment.contract.test.ts` и `verify-runtime.mjs`.
