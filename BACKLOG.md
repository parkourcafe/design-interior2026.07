Идеи вне scope M1/v0.1. Не код — очередь. Каждая строка ждёт своей фазы по лестнице из стратегии. M1 держим вокруг цепочки **Brief → Passport → Risks → Review → Proposal**.

## Future Module 2 — designer ↔ tools / AI tool hub

Модуль 2 — это слой инструментов дизайнера. Он может использовать паспорт и риски как входные данные, но не входит в текущий M1 MVP.

- **SketchUp / Adobe / render integrations** — экспорт/импорт, подготовка ассетов, генерация материалов для внешних инструментов.
- **MCP tool hub** — единая панель инструментов/агентов для дизайнера.
- **AI image/video generation hub** — генерация концептов, изображений, видео, moodboard-ассетов.
- **Concept Pack — расширение после MVP-slice** — текстовый style direction, moodboard outline, палитра, зоны и client-ready summary реализованы в первом Module 2 slice; в backlog остаются версии, редактор и визуальные концепции без нарушения guardrails по image generation.
- **Specs Engine** — объекты концепции → спецификации и ведомости.
- **Внешние интеграции** — любые API-интеграции за пределами текущего pre-sale контура.
- **Модуль 2 / AI tool hub дизайнера (только дизайнер)** — НЕ новая ступень, а имя для уже существующего: Concept Pack + Specs Engine (выше) и есть «инструменты производства» дизайнера; подключение внешних инструментов (SketchUp/Adobe/render) остаётся в guardrails. Зафиксировано, чтобы «хаб инструментов» из vision-документов не возвращался как новая идея. **Правило данных:** инструменты, которые подключает сам дизайнер, работают на его аккаунтах/ключах и свободны для его ассетов; но как только через инструмент идут клиентские данные из брифа — включаются ограничения провайдера и резидентности (152-ФЗ), как в основном runtime. Граница — по касанию клиентских данных, не по инструменту.

## Future Module 3 — designer + client + vendors/contractors workspace

Модуль 3 начинается после продажи. Это post-sale workspace, а не M1 pre-sale слой.

- **Клиентский портал** — переписка клиент ↔ дизайнер внутри сайта, тред по проекту, уведомления, вложения; начать с простых комментариев по проекту.
- **Vendor/contractor workspace** — подрядчики, строители, поставщики как участники проекта.
- **Contractor tasks** — задачи подрядчикам, ТЗ и запросы из проектных данных.
- **Project delivery management** — этапы реализации, согласования, статусы выполнения, post-sale контроль.
- **Procurement** — закупки, поставки, статусы заказов.
- **Materials catalog** — каталог материалов, спецификации и подборки для реализации.
- **Plan/fact construction budget** — строительный бюджет, факт расходов, отклонения.
- **Хранилище документов проекта** — договоры, сметы, КП, чертежи в одном месте (Project Brain).
- **AI-администратор проекта (оркестратор дедлайнов)** — поверх «портал + подрядчики»: единая картина исполнения — какая часть работы кем взята, что выполнено и к какому сроку должна быть; подсветка просрочек и блокировок по ролям. Это перенос pre-sale-механики «AI выносит несостыковку на решение человека» (движок рисков Модуля 1) на слой исполнения. Зависит от существования портала и участников-исполнителей — строить строго после них. Единственная ступень Модуля 3, которой не было в разделе 18 стратегии; зафиксирована здесь, чтобы не всплывать повторно как «новая идея». Не автоматизировать операционные решения и не предлагать в код чаще одного раза.
