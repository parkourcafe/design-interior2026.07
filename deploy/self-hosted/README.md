# RemHaOS на своём сервере (Россия): база и сайт

Зачем: по 152-ФЗ (ст. 18 ч. 5) данные граждан РФ при сборе записываются в базу на
территории России. У облачного Supabase нет региона в РФ, поэтому те же программы
Supabase ставятся на арендованный сервер в российском дата-центре. По оценке ПДн от
01.10.2026 анкеты, вход и КП тоже принимаются в России, поэтому сайт работает на том же
сервере (сервис `web`), а не на Vercel. Шрифты и медиа главной страницы отдаёт сам сайт;
AI на время пилота выключен (`REMHAOS_AI_ENABLED=false`).

Проверено 01.10.2026 на стенде, на этом комплекте:
- установка с нуля;
- все 145 миграций репозитория, повторный запуск применяет 0;
- перенос данных из старой базы (`scripts/cutover/`) со старыми паролями;
- путь в браузере: регистрация → бриф клиента → подтверждение паспорта → отправка КП
  → ссылка клиента;
- ночная копия: дамп базы и архив файлов.

- восстановление из этой копии на чистую базу (`restore.sh`): все счётчики совпали,
  вход в браузере работает;
- ограничение подбора пароля: после ~30 неудачных попыток с одного адреса — отказ 429;
- CORS: чужие сайты не получают доступа из браузера, сайт — получает.

Сайт в контейнере (`web`) проверен на стенде 01.10.2026: сборка образа, весь путь в
браузере через шлюз по двум именам (сайт и API) — см. раздел «Проверка» ниже.

Не проверены на стенде: реальная почта (SMTP), вход через Google, сертификат HTTPS
для настоящего домена, скачивание медиа главной страницы при сборке (на стенде нет
доступа к их CDN — собиралось с `MEDIA_MODE=cdn`).

## Что внутри

| Сервис | Что делает |
|---|---|
| `db` | PostgreSQL 17 (образ Supabase). Наружу не открыт: только 127.0.0.1 сервера. |
| `auth` | Регистрация, вход, письма (GoTrue). |
| `rest` | API к базе (PostgREST). Отдаются только разрешённые схемы. |
| `storage` | Файлы клиентов (планы, фото) — на диске сервера. |
| `gateway` | HTTPS (сертификат Let's Encrypt — автоматически): API по пути `/auth/v1`, `/rest/v1`, `/storage/v1` и сайт на своём адресе; адрес без `www` перенаправляется на сайт. |
| `web` | Сайт (Next.js), собирается из этого репозитория (`Dockerfile` в корне). |
| `backup` | Каждую ночь: роли, дамп базы и архив файлов в `./backups` (только для владельца), хранение ~14 дней. |

## Сервер

- Виртуальная машина в российском дата-центре: 2 vCPU, 4 ГБ RAM (сборка сайта требует
  ~3 ГБ; при 4 ГБ добавьте swap 2 ГБ), 40–50 ГБ SSD, публичный IPv4, Ubuntu 24.04.
- Включите у хостера **ежедневные снимки диска** — это копия вне `./backups`. Храните
  их не дольше 14 дней: удалённые по запросу аккаунты (DEC-047, 30 дней) не должны
  жить в копиях дольше.
- Управляемая база данных хостера («Managed PostgreSQL») не подходит: Supabase нужен свой
  образ базы с правами, которые хостеры не дают.

## Установка (один раз, ~30 минут)

1. **DNS и порты — до запуска.** У регистратора домена: записи `A` для
   `api.remhaos.com`, `www.remhaos.com` и `remhaos.com` → IP сервера (второе имя сайта
   шлюз перенаправляет на основное); дождитесь, пока они начнут открываться. В панели
   хостера (файрвол / группы безопасности) откройте входящие порты 80 и 443 (и 22 для
   SSH). Без этого сертификат HTTPS не выпустится.
2. **Docker.** На сервере:
   ```
   curl -fsSL https://get.docker.com | sh
   ```
3. **Код.**
   ```
   git clone https://github.com/parkourcafe/design-interior2026.07.git
   cd design-interior2026.07/deploy/self-hosted
   ```
4. **Секреты.**
   ```
   sh generate-env.sh api.remhaos.com https://www.remhaos.com
   ```
   Откройте `.env` и заполните `SMTP_*` (почтовый сервис), `SUPPORT_EMAIL` (адрес
   поддержки, должен принимать почту), `LEGAL_OPERATOR_*` (реквизиты оператора; пока
   пусто — юр. страницы помечены как проект), при необходимости `GOOGLE_*`.
   Если в пароле есть пробелы или символы `$ ; \` ` ` ` — заключите значение в одинарные
   кавычки: `SMTP_PASS='...'`.
   Второе имя сайта (без `www` или с `www`) шлюз перенаправляет на основное
   (`WEB_REDIRECT_ADDRESS`); если сайт открывается ещё по каким-то адресам — добавьте их в `ADDITIONAL_REDIRECT_URLS` через
   запятую, иначе ссылки из писем будут отклонены.
   Сохраните копию `.env` в менеджере паролей — без него сервер не восстановить.
5. **Запуск.** Первая сборка сайта — 5–10 минут.
   ```
   APP_COMMIT=$(git rev-parse --short HEAD) docker compose build web
   docker compose up -d
   docker compose ps          # все сервисы Up, db — healthy
   ```
6. **Миграции.**
   ```
   sh apply-migrations.sh     # в конце: MIGRATIONS_OK … всего: 145 (или больше)
   ```
7. **Проверка.** В браузере `https://api.remhaos.com/auth/v1/health` — ответ с `GoTrue`;
   `https://www.remhaos.com/api/health` — `"status":"ok"`, в `env` — `"ai_enabled":false`,
   и коммит.

## Сайт

Сайт собирается из `.env` этого комплекта: адрес API, ключ `ANON_KEY`, адрес сайта,
поддержка и реквизиты встраиваются при сборке, секреты (`SERVICE_ROLE_KEY`,
`PROJECTCEO_TOKEN_SECRET`, `REGIONAL_ROUTING_RECEIPT_SECRET`) передаются только при
запуске. После изменения `.env` или обновления кода:
```
APP_COMMIT=$(git rev-parse --short HEAD) docker compose build web && docker compose up -d web
```
Vercel для пилота не нужен. С новой базой все дизайнеры один раз войдут заново (старые
входы недействительны).

Регистрация идёт через сервер сайта, поэтому GoTrue видит её с адреса самого сервера:
при массовом наплыве регистраций (десятки за 5 минут) часть получит «попробуйте позже».
Вход по паролю и коду идёт из браузера и ограничивается по адресу клиента. Для пилота это
не мешает.

Если перед сервером когда-нибудь поставят балансировщик или защиту от DDoS хостера, все
клиенты будут видны с его адреса — тогда в Caddy нужно указать `trusted_proxies`.

Остальное — по `docs/audits/CUTOVER_RUNBOOK_2026-09-28.md`, раздел D.

## Перенос данных со старой базы

База закрыта для внешнего мира, поэтому перенос идёт через SSH-туннель со своего
компьютера:
```
ssh -N -L 15432:127.0.0.1:5432 user@<IP сервера>      # в отдельном окне
TARGET_DB_URL="postgresql://postgres:<POSTGRES_PASSWORD из .env>@127.0.0.1:15432/postgres"
```
Дальше — `scripts/cutover/transfer.zsh` и `transfer-files.mjs` по инструкции переезда
(для файлов `TARGET_SUPABASE_URL=https://api.remhaos.com`).

## Обновление

Если `.env` создан до 01.10.2026 (без сайта), сначала допишите в него строки, которых
нет: `API_HOST`, `WEB_SITE_ADDRESS`, `WEB_REDIRECT_ADDRESS`, `PROJECTCEO_TOKEN_SECRET`,
`REGIONAL_ROUTING_RECEIPT_SECRET`, `SUPPORT_EMAIL`, `LEGAL_OPERATOR_*` — образец даёт
`sh generate-env.sh` в пустой папке. Без них `docker compose` остановится с подсказкой.
```
git pull
sh apply-migrations.sh        # применит только новые миграции
APP_COMMIT=$(git rev-parse --short HEAD) docker compose build web
docker compose up -d          # перезапустит то, что изменилось
```

## Восстановление из копии

Основной способ — снимок диска у хостера (откат всего сервера). Из ночной копии:
```
ls backups/                     # выберите дату: roles-, db-, storage- одного времени
RESTORE_CONFIRM=yes sh restore.sh backups/db-<дата>.dump backups/roles-<дата>.sql backups/storage-<дата>.tar.gz
```
Скрипт не удаляет текущие данные — откладывает их в `volumes/*.before-restore-*`, —
поднимает чистую базу, восстанавливает роли и базу в три фазы, возвращает файлы и
печатает сводку: «неожиданных ошибок: 0» и число аккаунтов/проектов/КП. Проверено на
стенде 01.10: все счётчики совпали с исходными, вход в браузере работает.
Этим же скриптом база переносится на новый сервер: скопируйте туда `.env` и три файла.

## Удаление аккаунта по запросу (DEC-047)

Дизайнер запрашивает удаление в настройках — аккаунт сразу закрыт. В течение 30 дней
оператор уничтожает данные. С тем же SSH-туннелем, что для переноса (порт 15432):
```
# 1. Чьи сроки наступили (service role из .env)
NEXT_PUBLIC_SUPABASE_URL=https://api.remhaos.com SUPABASE_SERVICE_ROLE_KEY=<SERVICE_ROLE_KEY> \
  npx tsx scripts/account-purge.ts list
# 2. Уничтожить: сначала файлы (Storage API), затем база — одной транзакцией
NEXT_PUBLIC_SUPABASE_URL=https://api.remhaos.com SUPABASE_SERVICE_ROLE_KEY=<SERVICE_ROLE_KEY> \
PURGE_DATABASE_URL="postgresql://supabase_admin:<POSTGRES_PASSWORD>@127.0.0.1:15432/postgres" \
  npx tsx scripts/account-purge.ts purge <id дизайнера> "<ваше имя>"
```
В конце — квитанция с номером (`receiptId`): отправьте его дизайнеру как подтверждение.
Скрипт сначала делает пробный прогон в базе и только потом удаляет файлы. Если база
отказала (`ACCOUNT_PURGE_…`), ничего не удалено, файлы тоже: `FOREIGN_RECORDS` — дизайнер
работал в чужой студии или состоял в ней, такие записи решаются вручную; `LEGAL_HOLD` — удержание.
Отменить запрос до уничтожения (письмо дизайнера в поддержку):
`npx tsx scripts/account-retention-expiry.ts restore <id> "<причина>" "<ваше имя>"`.
Проверено на стенде 01.10.2026.

## Если миграция упала

`apply-migrations.sh` останавливается на первой ошибке и не отмечает миграцию
выполненной. Почти все миграции — одна транзакция и откатываются целиком: исправьте
причину и запустите скрипт снова. Три миграции без собственной транзакции
(`20260808050000`, `20260808060000`, `20260810040000`) могут оставить часть объектов; если
упала одна из них — пришлите вывод, повторно не запускайте (на чистой установке они
проверены и проходят).

## Безопасность

- `.env`, `volumes/` и `backups/` не коммитятся (`.gitignore`). Копии содержат
  персональные данные и создаются с правами только для владельца.
- Открыты наружу только 80/443. Сайт (порт 3000) снаружи недоступен — только через шлюз. Вход на сервер — по SSH-ключу; парольный вход по SSH
  отключите.
- Чужие сайты не получают доступа к API из браузера (CORS только для адреса сайта;
  проверено).
- Подбор паролей и кодов из писем ограничен по адресу клиента (проверено: отказ 429).
- Шаблоны писем Auth берёт с внутреннего адреса шлюза, снаружи он недоступен.
