## Методология

Анализ проводился по трём критериям:

1. **Семантическое пересечение** — схожесть формулировки цели пользователя
2. **Конкурентное ключевое слово** — вероятность борьбы за одни и те же поисковые запросы
3. **Сегмент аудитории** — одинаковый или разный пользователь стоит за интентом

Только совпадение по всем трём критериям означает истинный дубль, требующий слияния.

## Пары с пересечением

### Пара 1: DESIGNER_001 ↔ CLIENT_010

| Поле | DESIGNER_001 | CLIENT_010 |
|------|-------------|-----------|
| Название | Собрать информацию от клиента | Понять процесс работы |
| Сегмент | designer | client |
| Цель пользователя | Получить структурированную информацию без потери деталей | Узнать, как дизайнер будет работать над проектом |
| Тип интента | Informational | Informational |
| Приоритет | P1 | P1 |

**Оценка:** Тема одна — «сбор информации на старте проекта» — но точки зрения противоположны. Дизайнер хочет **получить** данные, клиент хочет **понять**, как этот процесс устроен. Поисковые запросы не пересекаются: дизайнер ищет «шаблон брифа», клиент ищет «как работает дизайнер».

**Вердикт:** Не дубль. Кросс-связь обязательна (красная пунктирная стрелка на графе).

### Пара 2: DESIGNER_003 ↔ CLIENT_002

| Поле | DESIGNER_003 | CLIENT_002 |
|------|-------------|-----------|
| Название | Рассчитать справедливую цену | Понять стоимость проекта |
| Сегмент | designer | client |
| Цель пользователя | Определить стоимость по чётким критериям | Узнать, сколько стоит дизайн-проект |
| Тип интента | Transactional | Informational |
| Приоритет | P1 | P1 |

**Оценка:** Оба интента касаются ценообразования, но с разных сторон рынка. Дизайнер ищет **инструмент расчёта**, клиент ищет **ориентир по рынку**. Разные типы контента: калькулятор vs. статья «из чего складывается цена».

**Вердикт:** Не дубль. Рекомендуется взаимная ссылка: страница для клиента → «узнайте, как дизайнер рассчитывает цену» и наоборот.

| Название | Выбрать стиль интерьера | Спланировать пространство | Выбрать материалы |

| Тип | Informational | Informational | Informational |

**Оценка:** Все три интента относятся к одной теме — «планирование дизайна». Они последовательны (сначала стиль, потом планировка, потом материалы), но каждый адресует отдельный вопрос. **Вердикт:** Не дубли, но требуют **единой контентной стратегии**. Рекомендуется создать хаб-страницу «Руководство по планированию дизайна», которая объединяет все три интента и ссылается на отдельные детальные страницы.

**Оценка:** Это наиболее близкая пара в реестре. Оба интента касаются **отслеживания изменений** в проекте. **Вердикт:** Граничный случай. Рекомендуется **объединить** в одну страницу «Управление изменениями и историей проекта» с двумя разделами. Это снизит риск каннибализации и создаст более полный материал.

## Итоговые рекомендации

**Истинных дублей нет.** Все 28 интентов адресуют уникальные потребности. Тем не менее, для повышения SEO-эффективности рекомендуется:

1. **Объединить** DESIGNER_008 и DESIGNER_010 в единую страницу «Управление изменениями и историей проекта» (единственная пара с реальным риском каннибализации).

2. **Создать хаб-страницу** для CLIENT_005 + CLIENT_006 + CLIENT_007 — «Руководство по планированию дизайна» — с внутренними ссылками на каждый отдельный интент.

3. **Добавить кросс-ссылки** между парами дизайнер ↔ клиент (пары 1, 2, 3), чтобы усилить внутреннюю перелинковку и показать обе стороны процесса.

4. **Использовать разные ключевые слова** для интентов с тематическим пересечением, чтобы избежать конкуренции страниц в выдаче Яндекса и Google.

## Дополнение при ревизии (05.08.2026)

### Пара 6: PARTNER_002 ↔ DESIGNER_008 / DESIGNER_010 — пропущена в первом проходе

| Поле | PARTNER_002 | DESIGNER_008 | DESIGNER_010 |
|------|-------------|--------------|--------------|
| Название | Отслеживать изменения проекта | Отследить историю решений | Управлять версиями и согласованиями |
| Сегмент | partner | designer | designer |
| Цель | Быть в курсе всех изменений в проекте | Полная история всех решений | Отслеживать версии и согласования |
| Приоритет | P2 | P2 | P2 |
| SEO-сложность | High | High | High |

**Оценка:** тема «отслеживание изменений проекта» проходит через три интента, а не через два. Первый проход рассмотрел только пару внутри сегмента designer и не заметил третьего участника. Сегмент у PARTNER_002 другой (подрядчик/архитектор, а не дизайнер), цель тоже другая — не управлять изменениями, а получать уведомления о них, — поэтому слияния не требуется. Но формулировка почти дословно совпадает с DESIGNER_010, и обе страницы претендуют на один и тот же запрос «отслеживать изменения проекта».

**Вердикт:** не дубль. При исполнении рекомендации №1 (слияние DESIGNER_008 + DESIGNER_010) ключевые слова партнёрской страницы нужно развести явно: у объединённой designer-страницы — «управление версиями и историей решений», у PARTNER_002 — «доступ подрядчика к изменениям проекта». Иначе слияние не снизит каннибализацию, а перенесёт её на границу сегментов.

### Расхождение с `intent-duplicates-source.md`

Исходный документ консолидации рекомендует «оставить все интенты раздельно» и предлагает объединить контент по трём другим осям: CLIENT_005 + CLIENT_006, DESIGNER_001 + DESIGNER_009, DESIGNER_005 + DESIGNER_002. Пара DESIGNER_008 ↔ DESIGNER_010 там не рассматривается вообще.

Актуальной считается рекомендация этого документа: единственное слияние — DESIGNER_008 + DESIGNER_010. Предложения исходного документа по DESIGNER_001 + DESIGNER_009 и DESIGNER_005 + DESIGNER_002 отклонены: это соседние шаги последовательности пресейла с разными целями пользователя и разными запросами — объединение схлопнуло бы два P1-интента в один и потеряло бы половину покрытия.
