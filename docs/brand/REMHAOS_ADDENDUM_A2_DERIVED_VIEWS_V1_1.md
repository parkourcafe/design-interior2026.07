# Аддендум A2 к Charter v0.4 — производные представления и Правила проверки

**Дата:** 27 июля 2026
**Уровень:** 2 (техническая архитектура, подчинена Charter v0.4 — см. Аддендум A1 §1)
**Предмет:** разбор предложения «Project Intelligence Layer v2.0», принятие его продуктового тезиса и замена девятикомпонентного слоя на один движок и класс производных представлений.

---

## 0. Короткий вывод

Продуктовый тезис верен и принимается: **система должна понимать состояние проекта лучше любого отдельного участника, и отвечать на вопрос «что должно произойти следующим», а не «что произошло».** Это правильная формулировка конкурентного преимущества, и она точнее, чем «много функций».

Архитектурная форма — девять компонентов в новом слое над модулями — не принимается. При разборе оказалось, что девять компонентов относятся к пяти разным категориям, и только один из них является новым движком.

| Компонент | Что это на самом деле |
|---|---|
| Project Memory | **уже есть** — Charter §11, ARCH V1.0 §4, `project_facts` |
| Evidence System | **уже есть** — `EvidenceItem`, Charter §14.3 п.10 |
| Cross-document Conflict Detection | **новый движок** — единственный |
| Design QA | тот же движок, другой набор правил |
| Readiness Engine | **запрос** — именованный набор правил, которые должны пройти |
| Project Health | **запрос** — счётчик непройденных правил по категориям |
| Recommendation Engine | **запрос** — непройденные правила, отсортированные |
| Confidence Engine | **дублирует** четыре статуса Charter §11; в числовом виде вреден |
| Timeline Intelligence | **заблокирован** — требует модели календарного плана, которой нет |

Итог: не девять компонентов и не новый слой, а **один движок правил + таблица правил + производные представления поверх существующего Project Graph.** Это не уменьшение амбиции. Это та же функциональность при вчетверо меньшей поверхности и без пятого модуля.

---

## 1. Почему не слой

Два дня назад решение было записано так: «Не создавать сейчас отдельный Module 5 Studio Intelligence, иначе появятся дублирование памяти, конфликтующие версии и четыре разных AI-системы». ARCH V1.0 §14 ставит «Не создавать Module 5 в доменной модели» первым пунктом запретов.

Признак модуля — не номер в названии. Признак модуля — **собственное состояние и собственные экраны.** Project Intelligence Layer в предложенном виде имеет и то и другое: Health Score, Readiness %, Recommendations и Confidence — это новые вычисляемые значения, которые нужно где-то хранить, пересчитывать, версионировать и показывать. Замкнутый цикл в конце предложения пишет результат обратно в Project Memory.

Поэтому формально это Module 5, только развёрнутый горизонтально. Содержательно — почти всё верно. Расходится форма, а не намерение.

**Решение [РЕШЕНО].** Новый слой не создаётся. Вводится:

1. **Validation Engine** (рабочее имя, публичного не получает) — один движок, исполняющий версионируемые правила над Project Graph.
2. **Класс производных представлений** — вычисляемые значения, которые **не являются фактами** и хранятся отдельно от `project_facts`.

Всё остальное из девяти — правила, запросы или отложено.

## 2. Validation Engine

### 2.1. Один движок, три семейства правил

```
ValidationRule
- id
- rule_key
- version
- family          -- completeness | consistency | policy
- scope           -- какие сущности сравниваются
- severity        -- blocking | warning | info
- cost_class      -- free_deterministic | metered_ai
- owning_module
- message_template
- resolution_hint -- какое действие закрывает правило
- status
```

`completeness` — «ожидаемый объект отсутствует». Это то, что в предложении названо Design QA: есть план мебели, есть план освещения, нет спецификации света, нет разверток кухни.

`consistency` — «два объекта утверждают разное». Это Cross-document Conflict Detection: 6 дверей в плане, 7 в спецификации, 8 в смете, 6 в закупке. Плитка 600×600 в спецификации и 600×1200 в развертках. Холодильник на плане кухни без розетки в электрике.

`policy` — «нарушено правило студии или проекта». Материал из запрещённых, поставщик вне списка, отклонение от ставки без обоснования.

Разделять их на отдельные движки нет причины: у всех трёх одинаковый цикл — прочитать срез графа, применить правило, при непрохождении создать объект.

### 2.2. Что движок производит

Непройденное правило создаёт `TechnicalConflict` — сущность уже введена в ARCH V1.0 §12 и признана новой в A1 §3.4. Дополняется полями:

```
TechnicalConflict
+ rule_key, rule_version
+ family, severity
+ compared_entity_ids[]     -- что именно сравнивалось
+ evidence_locators[]       -- где смотреть в каждом источнике
+ detected_at, detected_by  -- rule_engine | human
+ status                    -- open | resolved | accepted_as_is | not_applicable
+ resolution_change_request_id
```

`compared_entity_ids` и `evidence_locators` — обязательны. Конфликт без указания, какие именно две записи разошлись, бесполезен: пользователь не может ни проверить, ни оспорить. Это то же требование, что Charter §11 предъявляет к фактам через Источник.

### 2.3. Стоимость

Подавляющее большинство полезных правил **детерминированные**. Сравнить число позиций в спецификации с числом позиций в смете — это `SELECT`, а не вызов модели. Проверить наличие обязательного документа — это проверка существования записи.

`cost_class` в правиле обязателен (Аддендум A1 §2.4). Ожидаемое распределение: `free_deterministic` для completeness и числовых consistency-правил, `metered_ai` только там, где нужно суждение — сопоставление разноимённых позиций, чтение смысла из неструктурированного текста.

Это существенно: **главное конкурентное преимущество продукта почти целиком детерминированное.** Оно не зависит от качества модели, не тарифицируется и не может «уверенно соврать».

## 3. Производные представления **[РЕШЕНО]**

### 3.1. Правило хранения

Health, Readiness и рекомендации — не факты. У них нет Источника, их нельзя подтвердить человеком, они меняются сами при изменении входных данных.

**Они не пишутся в `project_facts` и не проходят через статусы Charter §11.** Смешение факта и вывода в одном хранилище обнуляет смысл provenance: невозможно отличить «клиент сказал 6 дверей» от «система посчитала, что готовность 68%».

Хранятся отдельно, вычисляются по чтению, кешируются, инвалидируются событием. **Фонового пересчёта по циклу нет.**

Замкнутый цикл из предложения — Memory → Analysis → Validation → Conflict → Health → Readiness → Timeline → Recommendation → Evidence → Memory — в такой форме не принимается по трём причинам: у него нет условия запуска, нет требования идемпотентности и нет границы стоимости. Цикл, который при каждом событии перезапускает анализ всех документов через модель, делает AI-себестоимость проекта неограниченной и не привязанной ни к какому действию пользователя. Charter §17.3 требует «AI cost per approved result» — у фонового пересчёта нет approved result, к которому его отнести.

Правильная форма: **событие → инвалидация → пересчёт затронутых правил при следующем чтении.** Не «система постоянно думает», а «система пересчитывает то, что изменилось, когда на это смотрят».

### 3.2. Readiness — набор правил, а не процент

```
ReadinessGate
- gate_key        -- tender_ready | construction_ready | procurement_ready | handover_ready
- required_rules[] -- какие правила должны пройти
- blocking_only   -- учитывать ли warning
```

Результат — не «Construction Ready 68%», а список:

```
Готовность к строительству: 12 из 18 обязательных пунктов

Не хватает:
— развертки кухни (документ отсутствует)
— спецификация света (документ отсутствует)
— согласование сантехники (ожидает Архитектора с 14.03)
— конфликт: двери, план 6 / спецификация 7
```

Разница не косметическая. 68% не говорит, что делать, и не проверяется. Список из шести пунктов — это одновременно диагноз, план действий и доказательство. И он защитим в споре, а процент нет.

### 3.3. Health — счётчик, а не оценка

Вместо `Project Health 91/100` с разбивкой по шести шкалам:

```
Открытых блокеров: 2
Предупреждений: 7
Ожидают согласования: 3 (самое старое — 11 дней)
Открытых Change Request: 4
Отклонение от бюджетной рамки: +14%
```

Каждая строка кликабельна и ведёт к конкретным записям.

**Обоснование отказа от числа.** В А1 §7.4 было принято, что 58/100 без рубрики создаёт точность, которой за ним нет. То же самое верно для 91/100, и в продукте — сильнее, чем в аудите. Оценка, показанная Заказчику, несёт подразумеваемую гарантию. Проект с оценкой 91 и обрушившимся потолком — это разговор, в котором придётся объяснять веса формулы. Продукт, который продаёт доказуемость, не может показывать синтезированное число со скрытым взвешиванием как главный индикатор.

Если позже понадобится один индикатор для списка проектов — это должен быть **худший статус среди гейтов**, а не среднее. «Заблокирован» / «есть предупреждения» / «чисто». Три состояния вместо ста.

### 3.4. Recommendations — сортировка, а не генерация

Непройденные правила уже содержат `resolution_hint`. Рекомендация — это упорядоченный список открытых правил и ожидающих действий, отсортированный по severity, возрасту и роли текущего пользователя.

То есть **самый «живой» компонент предложения оказывается почти бесплатным и полностью детерминированным.** Никакой генерации не требуется: если правило знает, что его закрывает, список сам является рекомендацией.

Ограничение [РЕШЕНО]: формулировка рекомендации остаётся в границах правила. Система говорит «не хватает спецификации света» и «конфликт по дверям», а не «проверьте гидроизоляцию» на основании общих соображений. Charter §16.1 запрещает AI утверждать и выпускать; рекомендация вне зафиксированного правила подходит к этой границе слишком близко и создаёт вопрос об ответственности за нерекомендованное. Расширение — отдельным решением, не сейчас.

## 4. Confidence — не число **[РЕШЕНО]**

Charter §11 уже задаёт четыре статуса каждого AI-вывода: **извлечено / интерпретировано / неизвестно / подтверждено человеком.** Это шкала доверия, и она рабочая, потому что каждое значение означает конкретное действие.

Числовая уверенность поверх неё — либо дубль, либо противоречие. И отдельно: `Confidence 76%` от языковой модели не означает 76%. Это некалиброванная величина, которую пользователь прочитает как вероятность. В продукте, чья позиция — «не утверждать больше, чем позволяют данные», показывать некалиброванное число как меру достоверности означает ровно то, против чего направлен сам принцип.

**Решение.** Числовая confidence остаётся **внутренним полем** на AI-извлечении и используется только для маршрутизации: ниже порога — обязательная человеческая проверка, выше — обычная очередь. В интерфейсе, в экспорте и в Evidence Pack показываются четыре статуса Charter §11 и ничего больше.

Замечание, ради которого стоит согласиться на потерю красивой цифры: «Недостаточно данных, Confidence 21%» и «Неизвестное, требует ответа заказчика» несут одно и то же сообщение, но второе говорит, кто и что должен сделать.

## 5. Timeline Intelligence — заблокирован отсутствующей моделью **[ОТКРЫТО]**

Это главная находка разбора.

Пример из предложения: «Через три дня начинается монтаж потолков. До начала рекомендуется проверить свет, согласовать люстры, сфотографировать разводку, закрыть Change Request #18.»

Для этого система должна знать, что монтаж потолков запланирован, и на какую дату. **Календарного плана в RemHaOS нет ни в каком виде.** В Charter §11 нет ни плана, ни срока, ни зависимости, ни вехи. В ARCH V1.0 §12 у Module 4 есть `SiteTask`, но задача — не расписание. В BRIEF §5 нет ни одной таблицы с датами работ. `ScheduleImpact` в списке M4 предполагает влияние на срок, которого пока не от чего отсчитывать.

Timeline Intelligence — не компонент интеллекта. Это надстройка над моделью данных, которой не существует, и которая по объёму сопоставима со всем M4: рабочие пакеты, вехи, зависимости, базовый план, факт против плана.

Без неё «Timeline Intelligence» деградирует до сортировки по дате создания записей — то есть до того, что уже описано в §3.4.

**Решение.** Компонент исключается из этого аддендума. Модель календарного плана — отдельное продуктовое решение уровня Charter, с собственной оценкой: нужен ли RemHaOS собственный планировщик или достаточно вех вокруг стадийных гейтов. Второе намного дешевле и, возможно, достаточно: большинство рекомендаций из примера привязаны не к дате, а к **переходу через гейт готовности** — «до перехода в Construction Ready закрыть вот это». Гейты уже есть в §3.2 и дат не требуют.

Это стоит проверить прежде, чем строить планировщик: **вероятно, 80% ценности Timeline Intelligence достигается гейтами без единой даты.**

## 6. Когда это можно строить

### 6.1. Флагманский пример недоступен ещё долго

Сквозная проверка «план мебели → спецификация → смета → закупка» требует структурированных Позиций из чертежей (M3), Спецификации (M3), Сметы (M3/M4) и Закупки (M4).

По AUDIT: M2 — 20/100, M3 — 18/100, M4 — 10/100. Все четыре входа флагманского примера находятся в модулях, где не построено практически ничего. Это архитектура для состояния продукта, до которого примерно полтора года.

### 6.2. Но проверить движок можно сейчас, на M1

Это самое полезное следствие разбора. В M1 **уже есть** данные, между которыми возможны настоящие расхождения: ответы брифа, Паспорт, состав работ, расчёт стоимости, версии КП, принятые карточки рисков.

Правила, реализуемые на текущей схеме, детерминированные, без единого вызова модели:

| Правило | Семейство | Что ловит |
|---|---|---|
| Площадь в брифе ≠ площадь в основании расчёта | consistency | ошибка в КП до отправки клиенту |
| Помещение в Паспорте не покрыто ни одним ScopeItem | completeness | недооценённый объём |
| ScopeItem без основания в расчёте стоимости | consistency | работа в составе, но не в цене |
| Расчёт превышает `BudgetExpectation` клиента более чем на N% | policy | **главная причина срыва сделки, видна до отправки** |
| Принятая карточка риска не отражена ни в составе, ни в цене | consistency | риск признан и проигнорирован |
| КП ссылается на версию Паспорта, изменившуюся после выпуска | consistency | устаревшее КП на руках у клиента |
| Ответ брифа изменён после построения Паспорта | consistency | Паспорт разошёлся с источником |

Семь правил. Все читаются из существующих таблиц. Ни одно не требует M2–M4.

Четвёртое из них — расхождение расчёта с бюджетной рамкой клиента — само по себе оправдывает работу: это самая частая причина, по которой пресейл заканчивается ничем, и сейчас дизайнер узнаёт о ней после отправки КП. `BudgetExpectation` уже введён в ARCH V1.0 §12 как сущность M1.

**Предложение.** Не включать это в текущий спринт — BRIEF §14 обоснованно запрещает расширение объёма, и вертикальный workflow должен закрыться первым. Но зафиксировать как **следующий спринт после него** и заложить `TechnicalConflict` и `ValidationRule` в модель данных сейчас, пока таблицы пустые.

Это даёт то, чего не даёт ни один архитектурный документ: **проверку главного конкурентного тезиса на реальных пилотных проектах через один спринт, а не через полтора года.** Если семь правил на M1 не находят ничего полезного у первых пилотов — тезис о cross-document intelligence нуждается в пересмотре до того, как под него построены M2–M4.

## 7. Итог: что принято

| Из предложения | Решение |
|---|---|
| Тезис «система понимает проект лучше участника» | **принят** как формулировка преимущества |
| Вопрос «что должно произойти следующим» | **принят** как продуктовая рамка |
| Cross-document Conflict Detection | **принят**, ядро Validation Engine |
| Design QA | **принят** как семейство `completeness` того же движка |
| Readiness | **принят** как набор правил; процент заменён списком непройденного |
| Health | **принят** как счётчик по категориям; оценка 0–100 отклонена |
| Recommendations | **принят** как сортировка непройденных правил; генерация вне правил отклонена |
| Evidence | уже есть; изменений не требует |
| Project Memory | уже есть; изменений не требует |
| Confidence как число в интерфейсе | **отклонён**; остаются четыре статуса Charter §11 |
| Timeline Intelligence | **отложен**; требует отдельного решения по календарной модели |
| Новый слой над модулями | **отклонён**; один движок и производные представления |
| Замкнутый цикл фонового пересчёта | **отклонён**; событийная инвалидация |

Девять компонентов сжались до одного движка, одной таблицы правил и класса производных представлений. Функциональность из предложения при этом сохранена целиком, кроме Timeline, который был заблокирован отсутствием данных, а не решением.

## 8. Что этот аддендум не меняет

Не отменяет и не смягчает: запрет на Module 5 (ARCH V1.0 §14, решение от 25.07.2026); список BRIEF §14; объём текущего спринта; девятнадцать правок Аддендума A1, включая пять блокирующих; открытые гейты Charter §18.3.

Не даёт разрешения начинать реализацию Validation Engine в текущем спринте. Из него в спринт входит только одно: **таблицы `validation_rules` и `technical_conflicts` в модели данных, пустые**, чтобы не мигрировать заполненную схему потом.

## 9. Замечание о темпе

За два дня портфель получил семь архитектурных документов: Charter v0.4, ARCH V1.0, AUDIT, BRIEF, MATRIX, Аддендум A1 и этот. Проект Bali накопил тринадцать версий `arch-reconciliation` ровно таким образом.
