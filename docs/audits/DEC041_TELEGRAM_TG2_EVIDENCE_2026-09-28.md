## Что сделано, по порядку владельца

1. **Кто написал.** Каждое событие из чата подписано: `verified_member` — это связанный Telegram-аккаунт
   с активным членством в проекте; `linked_non_member`; `unlinked`. Подпись ничего не разрешает.
   Бот по-прежнему создаёт только кандидатов, решает человек.
2. **Привязка и смена номера чата.**
   - Каждая смена статуса и номера пишется в append-only журнал `project_channel_binding_events` триггером.
   - Сообщения `migrate_to_chat_id` / `migrate_from_chat_id` переносят живую привязку автоматически.
   - Перенос идемпотентен по `update_id`. Парное сообщение из второго чата не пишет вторую запись.
   - Ключ — только числовой chat id. Название, телефон и имя не используются.
   - Если новый номер занят другой живой привязкой, перенос не выполняется. В лог уходит
     `chat_migration_target_bound`: нужен оператор.
3. **Файлы.**
   - Webhook записывает только метаданные (`file_id`) и только при включённом флаге «файлы».
   - Фоновый процесс `npm run bridge:telegram-attachments` делает следующее:
     - берёт вложения в аренду и спрашивает у Telegram путь;
     - скачивает файл с лимитом размера и проверяет его той же политикой, что и загрузку из интерфейса;
     - считает sha256 и кладёт файл в карантин существующего file intake (`scan_pending`).
   - Итог принимается только от держателя аренды.
4. **Флаги.** «Мост», «Файлы», «Уведомления» — на проект, по умолчанию выключены.
   - Включает только человек с `manage_project_integrations`, в панели Telegram проекта.
   - Каждое изменение — в append-only журнале с автором.
   - Выключенный мост не сохраняет сообщений. Выключенные уведомления не ставятся в очередь и не выдаются.
     Выключение снимает неотправленное.
   - Глобальный env-флаг остаётся главным.
   - Живые на момент установки миграции связи сохраняют «мост» и «уведомления». Автор этой записи в журнале —
     `system:migration`. «Файлы» им не включаются.
5. **Второй контур заморожен.** Webhook больше не отдаёт Telegram в контур «интеграция». Его данные и функции
   не тронуты.

## Не проверено и открытые вопросы

1. **Реальный Telegram — NOT_VERIFIED.** Бота и credentials нет, это вне разрешения.
2. **Нужно решение владельца: идентичность воркера файлов.** `create_file_intake_worker` выдан только
   `pi_worker_executor`, а логин-роли с этим членством ни в одном окружении нет. Так же и у импорта
   Google Drive. Пока этого нет, `REMHAOS_TELEGRAM_ATTACHMENTS_ENABLED` не включать: проход остановится на
   правах. Попытки теперь не сгорают.
3. **Нужно решение владельца: автор в file intake.** Функция эпохи R1 записывает автора
   `system:google-drive-import-worker` для любого воркера. Файл из Telegram будет подписан как импорт
   Google Drive. Связь сохраняется в `channel_attachments.file_intake_id`. Исправление требует изменить
   функцию R1, а это вне разрешения.
4. AP5 — через CI на PR, локально NOT_VERIFIED.
