# Переезд remhaos.com на новую базу — пошаговая инструкция

Решение владельца 28.09.2026: новая база Supabase из миграций репозитория, перенос
аккаунтов и проектов, старая база остаётся нетронутой (архив и откат). Регион новой
базы — после решения с юристом.

Всё, что ниже, делает владелец в браузере. Команды в терминале — только в разделах
«День переезда» и помечены. Ничего из этой инструкции агенты не выполняют сами.

Что есть на 28.09 (только чтение):
- старая база: проект Supabase `remhaos.com`, регион ap-northeast-1 (Токио), 13 входов
  (8 по паролю, 5 через Google), 9 дизайнеров, 30 проектов, 3 КП, 3 файла клиентов
  (7,7 МБ), последняя активность 12–15.09;
- сайт выкладывается с ветки `release` вручную (`vercel --prod`, автодеплой выключен);
- организация Supabase на тарифе Pro.

## Часть A — сейчас, не зависит от юриста

### A1. Включить защиту от утёкших паролей (1 минута, бесплатно)
supabase.com → проект `remhaos.com` → **Authentication** → **Sign In / Providers** (в
некоторых версиях — **Policies**) → блок **Password** → включить **Leaked password
protection** → Save. Supabase начнёт отклонять пароли из известных утечек.
Повторить в новом проекте после его создания (шаг C2).

### A2. Решить судьбу сборщика на Railway
Что это. В Railway есть проект `remhaos-market-harvest` с одним сервисом `collector`.
Это программа, которая собирает данные рынка (сайты дизайнеров, цены) и записывает их в
старую базу: 12 таблиц `market_harvest_*` и хранилище `firecrawl-raw` (17 826 файлов,
74 МБ). Последний запуск 21.08. Стоит денег каждый месяц.

Почему важно. Чтобы писать в базу, сборщик почти наверняка хранит **главный ключ**
базы (service role key). Этот ключ открывает всю базу, включая данные клиентов, в
обход любых ограничений. Переменные сервиса я не читал, чтобы не раскрыть секреты,
поэтому это предположение, а не факт.

Что нажать.
- **Сборщик не нужен:** railway.com → проект `remhaos-market-harvest` → сервис
  `collector` → **Settings** → внизу **Remove Service** → подтвердить. Данные,
  которые он уже собрал, остаются в старой базе.
- **Пока не решили:** тот же экран → **Pause** (если кнопка есть) — сервис
  останавливается, деньги не списываются, можно вернуть.
- **Нужен:** ничего не трогать до переезда. К новой базе сборщик не подключается:
  данные рынка остаются в старой базе как архив.

### A3. «Выпустить новый главный ключ» — что это и нужно ли
Главный ключ (service role key) — пароль, дающий полный доступ к базе. «Выпустить
новый» = сделать старый недействительным, чтобы все, у кого он есть (сборщик, старые
настройки, чужие компьютеры), потеряли доступ.

**Для переезда отдельно делать ничего не нужно:** у новой базы ключ новый сам по себе.
Старый ключ перестанет что-либо значить, когда старый проект будет удалён (шаг D3).
Если хотите закрыть доступ к старой базе раньше: supabase.com → `remhaos.com` →
**Settings** → **API Keys** → у service role → **Rotate**. После этого сборщик (если он
ещё работает) и старый сайт потеряют доступ к базе — делать только после переезда.

## Часть B — с юристом (от этого зависит создание новой базы)

Вопросы собраны в `OWNER_LAWYER_DECISIONS_2026-09-28.md`. Коротко:
- **B1. Регион** новой базы: Токио / Франкфурт / другой. Региона РФ у Supabase нет; если
  нужна РФ — это отдельный хостинг, не Supabase, и отдельная задача.
- **B2. Кто оператор данных клиента**: дизайнер (а сервис — обработчик по поручению) или
  сервис. От этого зависит, кто отвечает за сроки хранения и удаление.
- **B3. Срок хранения** после завершения проекта или удаления аккаунта и что потом:
  удалить или обезличить.
- **B4. Тексты** политики, согласия, условий и реквизиты оператора.

Про «хранить год» и расходы: вся база — единицы мегабайт, файлы клиентов — 7,7 МБ.
Внутри тарифа Pro хранение такого объёма ничего не добавляет к стоимости самой базы.
«Кэш владельца аккаунта» хранением не является (временный, очищается сам). Правильный
путь — выгрузка: дизайнер скачивает свои данные (экспорт паспорта в продукте есть), а
сервис после выгрузки может удалять раньше — если юрист подтвердит роль обработчика.

## Часть C — подготовка новой базы (после решения B1)

### C1. Создать проект Supabase
supabase.com → организация `Remhaos+ Pet ID` → **New project**:
- Name: например `remhaos-prod-2`;
- Database password: сгенерировать, сохранить в менеджере паролей (понадобится в C6);
- Region: по решению B1;
- Create. Ждать 2–3 минуты, пока статус станет Active.

Стоимость: проект в организации на Pro — точную цифру покажет Supabase на этом экране.

### C2. Настроить вход
Проект → **Authentication**:
1. **URL Configuration**: Site URL = `https://www.remhaos.com`; Redirect URLs — добавить
   `https://www.remhaos.com/**` и `https://remhaos.com/**`.
2. **Sign In / Providers → Email**: включён; **Confirm email** — включить;
   **Leaked password protection** — включить (см. A1).
3. **Sign In / Providers → Google**: включить, вставить Client ID и Client Secret из
   Google Cloud Console того же OAuth-клиента, что работал со старым проектом. В Google
   Cloud Console в **Authorized redirect URIs** добавить адрес, который покажет Supabase
   на этом экране (вида `https://<новый-ref>.supabase.co/auth/v1/callback`).
   Без этого 5 аккаунтов, входивших через Google, не смогут войти.
4. **Emails → Templates**: вставить содержимое `supabase/email-templates/confirm_signup.html`
   в **Confirm signup** и `magic_link.html` в **Magic Link** (инструкция в
   `supabase/email-templates/README.md`).
5. **Emails → SMTP Settings**: включить **Custom SMTP** и указать данные вашего почтового
   сервиса (например, Resend: host `smtp.resend.com`, порт 465, user `resend`, пароль —
   API-ключ, отправитель — адрес на подтверждённом домене). Без своего SMTP Supabase
   отправляет не более нескольких писем в час — регистрация упрётся в лимит.

### C3. Хранилище
Проект → **Storage**: бакеты `client-uploads` и `contract-documents` создаст миграция
(C4), вручную ничего создавать не нужно. Проверить после C4, что они появились и
помечены как private.

### C4. Применить миграции репозитория
Терминал на вашем компьютере, в папке репозитория на ветке `claude/audit-fixes-3-6`
(или там, куда она будет влита):
```
npx supabase link --project-ref <ref нового проекта>
npx supabase db push
```
`db push` спросит пароль базы из C1. Должны примениться все 145 миграций
(на чистом образе Supabase это проверено 28.09: `CLEAN_BOOTSTRAP_OK migrations=145`).
Если что-то упало — не продолжать, прислать вывод.

### C5. Ключи и секреты для Vercel
Проект → **Settings → API Keys**: скопировать **Project URL**, **publishable (anon)** и
**service role** ключи. Сгенерировать два новых секрета по 32+ случайных байта
(например, командой `openssl rand -base64 48`) — для `PROJECTCEO_TOKEN_SECRET` и
`REGIONAL_ROUTING_RECEIPT_SECRET`. Старые значения переносить можно, но новые
безопаснее; после смены все дизайнеры один раз войдут заново.

## Часть D — день переезда

Порядок важен. Ориентир по времени: 30–60 минут, лучше в тихое время (последняя
активность на сайте — середина дня по будням).

### D1. Заморозить старую базу (только чтение)
supabase.com → `remhaos.com` → **SQL Editor** → выполнить:
```sql
alter role authenticator set default_transaction_read_only = on;
select pg_terminate_backend(pid) from pg_stat_activity where usename = 'authenticator';
```
После этого сайт на старой базе ничего не сможет записать (регистрация, брифы, КП);
чтение работает. Это гарантирует, что при переносе ничего не потеряется.

### D2. Перенести данные
Терминал (нужен `psql` 15+ и Node 22). Строки подключения обеих баз — из
**Settings → Database → Connection string (Direct)** каждого проекта, с паролем.
```
SOURCE_DB_URL='postgresql://postgres:<пароль-старой>@db.ztnycrchwxqczqbyegnp.supabase.co:5432/postgres' \
TARGET_DB_URL='postgresql://postgres:<пароль-новой>@db.<новый-ref>.supabase.co:5432/postgres' \
  zsh scripts/cutover/transfer.zsh
```
Ожидаемый конец вывода: строки `OK` по каждой таблице, `OK ревизии паспорта`, и
`TRANSFER_OK`. Скрипт читает старую базу только для чтения, пишет одной транзакцией и
отказывается работать, если новая база не пуста.

Файлы клиентов:
```
SOURCE_SUPABASE_URL=https://ztnycrchwxqczqbyegnp.supabase.co SOURCE_SERVICE_ROLE_KEY=<старый service role> \
TARGET_SUPABASE_URL=https://<новый-ref>.supabase.co TARGET_SERVICE_ROLE_KEY=<новый service role> \
  node scripts/cutover/transfer-files.mjs
```
Ожидается `FILES_TRANSFER_OK` (3 файла).

Если вместо этого хотите, чтобы перенос выполнил я: дайте обе строки подключения и оба
service-role-ключа в этой сессии — после переноса удалите пароли/ключи старого проекта
(A3).

### D3. Переменные Vercel
vercel.com → проект `design-interior2026-07` → **Settings → Environment Variables**,
окружение **Production**. Заменить:
- `NEXT_PUBLIC_SUPABASE_URL` — Project URL нового проекта;
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (и `NEXT_PUBLIC_SUPABASE_ANON_KEY`, если есть) —
  publishable/anon ключ нового проекта;
- `SUPABASE_SERVICE_ROLE_KEY` — service role нового проекта;
- `PROJECTCEO_TOKEN_SECRET`, `REGIONAL_ROUTING_RECEIPT_SECRET` — из C5.
Проверить, что заданы: `NEXT_PUBLIC_APP_URL=https://www.remhaos.com`,
`NEXT_PUBLIC_SUPPORT_EMAIL`, `NEXT_PUBLIC_LEGAL_OPERATOR_*`, `LLM_PROVIDER` и ключ
провайдера. Переменные `*_US` оставить пустыми.
Старые значения сохранить в менеджере паролей — это откат.

### D4. Выложить сайт
Терминал, в репозитории:
```
git checkout release
git merge --no-ff claude/audit-fixes-3-6
git push origin release
vercel --prod
```
(merge и деплой — только владелец; агенты этого не делают.)

### D5. Проверить на живом сайте (10 минут)
1. Открыть https://www.remhaos.com — главная открывается, в подвале документы
   подписаны «проекты, на согласовании».
2. Войти как существующий дизайнер по паролю → кабинет со старыми проектами.
3. Войти как дизайнер с Google → кабинет.
4. Открыть старую ссылку на бриф `/i/…` любого незавершённого проекта → бренд дизайнера
   виден.
5. Открыть старую ссылку на КП `/p/…` → КП открывается.
6. Зарегистрировать новый тестовый аккаунт → письмо подтверждения пришло, вход прошёл.
7. Создать проект, заполнить бриф как клиент с чекбоксом согласия, подтвердить паспорт,
   отправить КП, открыть ссылку клиента.
8. Настройки → запрос удаления аккаунта показывает статус (раньше давал ошибку).
Что-то не так — откат (D6), потом разбираемся.

### D6. Откат (если нужно)
1. Vercel → Environment Variables → вернуть старые значения из D3.
2. Vercel → **Deployments** → у предыдущего успешного деплоя **⋯ → Promote to Production**.
3. Старая база → SQL Editor:
   `alter role authenticator reset default_transaction_read_only;`
   и снова `pg_terminate_backend` как в D1.
Старая база всё это время была нетронута, данные не теряются. Новый проект можно удалить
или оставить для повторной попытки.

## Часть E — после переезда (через 2–4 недели спокойной работы)

- **E1.** Сделать архив старой базы: supabase.com → `remhaos.com` → **Database →
  Backups** → скачать последний бэкап; хранилище `client-uploads` уже перенесено;
  `firecrawl-raw` (сборщик) — скачать, только если эти данные нужны.
- **E2.** Удалить сервис `collector` на Railway, если ещё не удалён (A2).
- **E3.** Удалить старый проект Supabase: **Settings → General → Delete project**. Это
  убирает копию данных в Токио и её ежемесячную стоимость. Делать только после E1.
