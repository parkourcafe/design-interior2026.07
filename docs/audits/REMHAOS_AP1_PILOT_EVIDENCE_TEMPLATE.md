## 2. Воспроизведение стенда скриптом

```
AP1_DB_URL=… AP1_CONFIRM_DISPOSABLE=yes \
  tests/ap1/environment/bootstrap-disposable.zsh bootstrap
```

Вставить вывод как есть (строка подключения в выводе не печатается):

```text
AP1_BOOTSTRAP_START target=…

AP1_STAND_SHAPE …
```

|---|---|---|

скрипт обязан воспроизводить стенд сам.

## 3. Блокер `92060e3` — воспроизведён или опровергнут

Речь о `SECURITY DEFINER`-функции, принадлежащей `pi_table_owner`, которая
читает актора через `auth.uid()`. На managed Supabase грант
`usage on schema auth` молча не применяется (WARNING, не ERROR), миграция
отчитывается об успехе, а падает живой аутентифицированный вызов
(AP1_RUNBOOK.md §2b).

| | |
|---|---|
| **Вердикт** | _воспроизведён / не воспроизводится_ |
| Чем доказан | |
| `managed_auth_references` в `AP1_DB_OK` | |
| Прогон шёл БЕЗ обхода `grant authenticated to pi_table_owner` | `AP1_AUTH_WORKAROUND_GRANT_ABSENT` — да/нет |
| Живой RPC от аутентифицированной сессии отработал | |
| Чужая организация/пакет отклонены `P1103` | |

Вердикт «не воспроизводится» имеет силу только вместе со строкой
`AP1_AUTH_WORKAROUND_GRANT_ABSENT` из того же прогона. С заплаткой зелёный
результат доказывает заплатку, а не фикс (AP1_RUNBOOK.md §6).

## 4. Пять ролевых пользователей

```
AP1_CONFIRM_DISPOSABLE=yes npm run provision:ap1
```

Скрипт создаёт только auth-identity. Членства раздаются штатным
invitation-потоком от лица owner — service role человеческих операций не
выполняет (AGENTS.md).

| `builder` | `builder` | | invitation от owner | |
| `client` | `client_approver` | | invitation от owner | |
| `guest` | — | | отдельный guest grant, без членства | |

Адреса ролевых пользователей в отчёт не вставляются.
