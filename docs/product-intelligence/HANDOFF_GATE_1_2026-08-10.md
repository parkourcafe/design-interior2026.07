## 2. Вторая задача: `publish_release`

**Найденный дефект.** Контракт команды по-прежнему требует от клиента полный
дескриптор с собственным `semanticHash` (`command-contract.ts`,
`publish_release`), а собрать его из браузера нечем: ни хелпера, ни preview, ни
токена.

Это ровно тот дефект, который решение A′ вылечило у `publish_baseline`, на шаг
дальше по цепочке. **Лечится тем же способом**, и все кирпичи уже написаны:

| Кирпич | Файл | Что переиспользовать |
|---|---|---|
| правило состава | `lib/project-intelligence/modules/decisions/baseline-composition.ts` | образец: неизвестный вид — ошибка, а не пропуск |
| снапшот-токен | `.../baseline-snapshot.ts` | `buildBaselineSnapshot` / `confirmBaselineSnapshot` |
| оркестровка | `command-service.ts`, ветка `publish_baseline` | образец порядка: сверка токена **до** любой записи |
| preview | `live-read-port.ts`, affordance `publish_baseline` | токен как `commandTargetId` |
| экран | `components/projectceo/project-workspace.tsx` | кнопка шлёт только токен |

Дескриптор релиза (`command-contract.ts`, `publish_release`) содержит
`exactRevisionRefs` (sources/requirements/assumptions/decisions/selections),
`baselineId`, `packageId`, `previousVersionId`, `organizationId`, `projectId`,
`schemaVersion`, `semanticHash`. Всё это выводимо из baseline, который только
что опубликован, — состав релиза есть состав его baseline.

**Открытый вопрос, который надо решить до кода:** где считать `semanticHash`
релиза. Для baseline он считается в application-слое TS-хелпером, и это
осознанно оставленный долг двойной канонизации (см. §5). Для релиза стоит
решить сразу: либо тот же путь ради единообразия, либо перенос внутрь RPC.

## 4. Инварианты, которые нельзя нарушить

Проверены и держатся; их нарушение — не «ускорение», а откат назад.

1. **Миграции только additive.** Каждая — строка в реестре. Правка принятой
   миграции запрещена.
2. **Чтения версионированы.** v7 → v8; менять поведение отданной версии нельзя,
   только новая.
3. **Состав baseline не приходит с клиента.** `baselineDescriptor` удалён из
   контракта сознательно: база принимает неполный baseline молча, значит
   правило полноты обязано быть недостижимым с клиента.
4. **Поверхность не обещает того, чего сервер не выполнит.** Дважды за сессию
   нарушение этого правила давало 500 и 409 у пользователя.
5. **Флаг M4 выключен**, и запрет держится на **двух** границах — приложения и
   базы. Одна без другой запрета не создаёт.
6. **Guardrail-тест на классификацию.** Любая новая команда в контракте роняет
   CI, пока её не отнесут к инкременту 1, инкременту 2 или «не модуль 4».

   отдельного решения о воркерном контуре.

## 9. Что произошло за смену — три находки гейта

Записано не ради истории, а потому что каждая объясняет решение в коде.

1. **Ревью источника отвечало 500.** Причина — граница схем:
   `project_intelligence_api` не отдана Data API. Починено дверью. Первый дефект
   маскировал второй.
2. **Поверхность предлагала ревью ревизии, которой нет в графе.** Обнажилось,
   когда первый дефект убрали: 409 `stale_state`, а на живой базе —
   `P1004 REVISION_STALE` с `currentRevisionId: null`. Починено чтением v8.
3. **M4 был открыт на уровне базы для любой аутентифицированной сессии.**
   `projectceo_m4_api` отдана Data API, её команды выданы `authenticated` —
   `command-service.ts` обходился прямым вызовом PostgREST. Закрыто миграцией.

Дважды в этих находках ошибалась я, и оба раза меня поправил гейт или
собственный негативный контроль. Это и есть довод держать AP5 блокирующим.
