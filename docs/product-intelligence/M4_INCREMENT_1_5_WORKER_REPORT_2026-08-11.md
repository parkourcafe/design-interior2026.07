## 1. Зачем этап существует

Гейт 2 доказал инкремент 1 браузером и там же нашёл, что A6 §1.1 ошибается:
у выдачи воркерная предпосылка ЕСТЬ. `distribute_release` адресуется артефакту
выпуска, а собрать артефакт может только система — у
`build_release_artifact` права лишь у `service_role`, и запись помечается
`system:projectceo-product-worker`. Человеческой двери к ней нет и по замыслу
не будет.

В прогоне AP5 195 этот шаг изображал psql-скрипт. Он доказывал поведение базы,
но не существование воркера, — то есть цепочка «выпуск → выдача» в продакшене
всё равно не замкнулась бы. Этап закрывает ровно этот разрыв.

## 2. Что построено

| Слой | Файл |
|---|---|
| Системное чтение очереди | `supabase/migrations/20260811030000_projectceo_release_artifact_worker_read.sql` |
| Планировщик (детерминизм, без сети) | `lib/project-intelligence/workers/release-artifact/planner.ts` |
| Прогон (исходы гонки) | `lib/project-intelligence/workers/release-artifact/runner.ts` |
| Точка входа | `scripts/run-release-artifact-worker.ts`, `npm run worker:release-artifacts` |
| Адаптер (граница с базой) | `ProjectBrainWorkerPostgresAdapter.listReleaseArtifactBacklog` |

Переиспользовано, а не написано заново: `buildReleaseDescriptor()` и
`ProjectBrainWorkerPostgresAdapter.buildReleaseArtifact()` — как требует DEC-030.
У `buildReleaseDescriptor` сужен тип входа до полей, которые он действительно
читает: воркер собирает версию из очереди, где нет ни `publishedAt`, ни
`publishedBy`, и выдумывать их ради формы типа он не должен.

## 3. Требования DEC-030 и чем каждое закрыто

| Требование | Чем закрыто |
|---|---|
| Сам находит выпущенные версии без артефакта | `list_release_artifact_backlog`; очередь исключает версии с артефактом — DB4 41 |
| Переиспользует существующие функции | `planner.ts` зовёт `buildReleaseDescriptor`, `runner.ts` — `buildReleaseArtifact` |
| Только системная identity | обе RPC выданы только `service_role`; `authenticated` получает `insufficient_privilege` на реальном вызове — DB4 41 |
| Детерминированные `artifactId` и ключ идемпотентности | `releaseArtifactId` (sha256 от арендатора+проекта+версии, фиксированная длина) и `releaseArtifactIdempotencyKey`; юнит-тесты на длину, стабильность и разделение арендаторов |
| Переживает повтор | повтор с тем же ключом → `already_present`; DB4-гонка проверяет отсутствие дубля после повтора |
| Переживает параллельный запуск | два параллельных вызова: обе транзакции успешны, ровно один `replay: false`, артефакт один — `DB4_RELEASE_ARTIFACT_WORKER_OK` |
| Переживает потерю ответа | ключ не включает ревизию состояния, поэтому повтор попадает в тот же ключ; `idempotency_conflict` трактуется как «уже сделано», а не как отказ |
| Не создаёт человеческого HTTP/RPC-доступа | ни маршрута, ни команды в контракте; запускается процессом |
| Не открывает M4 в production | флаг модуля и отозванные права не тронуты; миграция guard-блоком проверяет, что `build_release_artifact` по-прежнему недоступна `authenticated` |

## 4. Доказательство этапа

| Пункт решения | Где проверяется |
|---|---|
| `authenticated` не вызывает воркер | `tests/db4/41_release_artifact_backlog.sql` — реальный вызов из-под роли, `insufficient_privilege` до тела функции; там же — что сборка артефакта осталась системной |
| Два параллельных запуска создают один артефакт | `tests/db4/run-concurrency.zsh` — `DB4_RELEASE_ARTIFACT_WORKER_OK` |
| Повтор после перезапуска не создаёт дубль | та же гонка + повторный вызов; на живом стеке — второй запуск воркера в звене 9 AP5 (`scanned: 0`) |
| Пустая очередь — безопасный no-op | юнит-тест «is a safe no-op on an empty queue»: ни одного вызова записи; на живом стеке — повтор в звене 9 |
| AP5 использует настоящий runner | `tests/ap5/release-worker.ts` зовёт `npm run worker:release-artifacts`; psql-мост и его SQL удалены |

Сверх списка: очередь не отдаёт ни одного поля сверх нужного для дескриптора
(DB4 41) — системный процесс не получает ни имён, ни контактов, ни авторства.

## 5. Границы этапа — что НЕ построено

По DEC-030 не разрешено и не построено: расчёт влияния, вехи, обработка фото,
сборка передачи. Инкремент 2 модуля 4 не начат и остаётся закрытым на обеих
границах. Воркерного фреймворка (планировщика задач, очередей, ретраев с
бэкоффом) в этом этапе нет: один воркер — один проход — один отчёт.

## 6. Как проверить руками за 5 минут

```bash
npm run lint && npm run typecheck && npm run test && npm run build
zsh tests/db4/run.zsh                              # PG16
PI_DB_IMAGE=postgres:17-alpine zsh tests/db4/run.zsh
```

В выводе DB4 обязаны быть `DB4_RELEASE_ARTIFACT_BACKLOG_OK` и
`DB4_RELEASE_ARTIFACT_WORKER_OK`.

Воркер против одноразового стенда:

```bash
npm run worker:release-artifacts     # печатает отчёт даже на пустой очереди
npm run worker:release-artifacts     # повтор: scanned 0, created 0
```

## 7. Известные ограничения

1. **Расписания нет.** Воркер делает один проход и завершается; чем его
   запускать в продакшене (cron, очередь, вызов после публикации) — отдельное
   решение вместе с production-включением M4.
2. **Формат один — `logical_json`.** PDF/XLSX/CSV контракт допускает, но P0 их
   не выпускает, и воркер их не собирает.
3. **`stale_state` не ретраится внутри прохода.** Исход честно отражён в
   отчёте; следующий проход прочитает очередь заново. Ретрай внутри прохода —
   это уже воркерный фреймворк, которого DEC-030 не разрешает.
4. **Цикл 7 остаётся открытым и красным** — без изменений.
