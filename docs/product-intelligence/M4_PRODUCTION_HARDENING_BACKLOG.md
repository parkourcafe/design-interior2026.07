# M4 Production Hardening — backlog

**Статус:** заведён 11.08.2026 вместе с постройкой инкремента 1.
**Правило то же, что у `M3_PRODUCTION_HARDENING_BACKLOG.md`:** каждый пункт
**обязателен до внешнего production-пилота M4** и **не блокирует** дальнейшую
разработку. Пункт закрывается кодом с тестом, не галочкой.

| # | Что | Почему отложено |
|---|---|---|
| 1 | **Воркер артефакта выпуска.** `distribute_release` адресуется артефакту, а собрать его может только система (`build_release_artifact`, права у `service_role`). Человеческой двери нет и по замыслу не будет | Найдено гейтом 2: A6 §1.1 считал инкремент 1 свободным от воркерных предпосылок, и для выдачи это неверно. Воркерный контур — отдельное решение владельца, к тонкому P0 он не относился. Без него цепочка «выпуск → выдача» в продакшене не замыкается, и включать инкремент 1 бессмысленно |
| 2 | **Две двери у выдачи и подтверждения.** Кроме request-bound RPC, которые зовёт приложение, живут прежние `projectceo_product_api.distribute_release` / `acknowledge_release` | Их семантику (чужой получатель → `P1103`, чужой хеш → `P1107`) проверяет `tests/db4/20_product_operations.sql`. Отозвать их насмерть сегодня значит потерять это покрытие; свести к одной двери — вместе с переносом проверок на request-bound версии |
| 3 | **Авторитетный DB-state включения модуля** вместо скрипта среды: кто, когда, на каком основании включил M4, с аудитом; env-флаг поверх него как дополнительный hard-off | Тот же пункт, что у M3 (там он записан как предпосылка backlog). Пока его нет, `enable-m4-increment-1.sql` остаётся механизмом одноразовой среды, и production-включение запрещено |
| 4 | **Покрытие предпосылки приёмки вехи** — три теста в `live-read-sanitization.test.ts` проверяли «приёмка предлагается только после принятия всех фото»; сегодня операция закрыта как инкремент 2, и тесты проверяют закрытость | Возвращается вместе с открытием инкремента 2; фикстуры трёх состояний оставлены в тесте намеренно, чтобы возврат был правкой утверждений, а не написанием заново |
| 5 | **Роли выдачи в приложении выведены, а не перечислены.** Сейчас `command-service.ts` сравнивает `scope.role` со списком `owner_lead` / `architect`; база выводит то же из `_role_capabilities` | Расхождение уже случалось (до 11.08 приложение пропускало только `owner_lead`, а поверхность предлагала выдачу и архитектору). Лечение — общий источник capability для сервера, а не второй список |
