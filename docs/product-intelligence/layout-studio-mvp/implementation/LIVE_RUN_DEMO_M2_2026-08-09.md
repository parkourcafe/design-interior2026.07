прогнан настоящим Chromium против прод-сборки Next поверх одноразового стека.

## Что значит «живой»

| Слой | Что реально работало |
|---|---|
| База | PostgreSQL 16.13, одноразовый локальный кластер; вся цепочка из 31 миграции применена с нуля |
| Auth | настоящий GoTrue, собранный из исходников `github.com/supabase/auth` (пин ef6587a); пользователи созданы admin-API, вход — паролем через продуктовую страницу `/login` |
| Data API | настоящий PostgREST 12.2.12 (статический бинарь), схемы `public` + все `*_api` контура |
| Шлюз | маршрутизация путей `/auth/v1→GoTrue`, `/rest/v1→PostgREST` — роль Kong, без собственной логики |
| Приложение | `next build` + `next start`, флаг `ARCHIDOM_LAYOUT_STUDIO_ENABLED=true` |
| Браузер | Chromium 1194 (Playwright), реальные клики; дизайнер и клиент — два настоящих GoTrue-пользователя |

Ни одного мока между браузером и Postgres. Публикация версий, регистрация
комнаты и материалы шли через command API контура (`/api/projectceo/commands`)
и его SQL-валидацию (пересчёт семантического хеша в Postgres).

## Что прогон дал продукту (исправлено в этой же ветке)

1. **Отказ хранилища версий больше не роняет редактор.** 403/500 на чтении
   пакета превращали открытие планировки в «ошибку загрузки черновика», хотя
   черновик загрузился. Теперь деградация честная: версии пусты, причина в
   консоли, черновики и чекпойнты работают.
2. **Форма строк чтения контура.** Строки append-only ревизий несут поля во
   вложенном `payload`; выдуманный тестом плоский вариант молча отфильтровывал
   все настоящие строки. Разбор и мок теста переведены на настоящую форму.
3. **Скрытая цена ≠ 0 ₽.** Чтение контура редактирует финансовые поля для
   не-финансовых ролей (`v_financial`). Панель бюджета теперь говорит «цена
   скрыта правами доступа», а не показывает ложный ноль.
4. **versionId уникален на весь пакет, не на документ.** «V1» второго
   документа отклонялся хранилищем (`VERSION_ID_ALREADY_EXISTS`). Версии
   минтятся как `<documentId>@<n>`, человеку показывается «V‹n›».
5. **Чтение бюджета — по привязке.** Пакетный актёр не имеет права на
   проектный UI-роут; бюджетный мир читается серверным действием
   `workspaceRead` роута планировки через authenticated-read RPC контура,
   от имени пользователя, без service role.
6. **Панель привязки понимает пакетных актёров** (fallback на пакет из
   портфолио) и **миниатюра витрины** читает проектным чтением без
   `packageId` (клиент — проектный актёр).

## Находки для параллельного чата (их сторона)

1. **Scope-метка чтения.** `get_project_workspace_read_v6` для проектного
   актёра с `package_id` сужает ДАННЫЕ до пакета, но оставляет
   `accessScope='project'` — а роут `/projects/[id]/layouts` требует метку
   `package` и падает 500 (internal), не 403. Проектный актёр не может
   пройти публикацию их клиентом.
2. **Финансовая видимость против публикации.** `v_financial` берётся из
   ПРОЕКТНОЙ роли; публикация требует пакетного scope. Один человек не может
   одновременно видеть цены и публиковать версии. Нужна их резолюция
   (например, `v_financial` учитывает пакетную роль architect).
3. **Пакетные capabilities architect'а.** `_package_role_capabilities('architect')`
   не выдаёт `revise_decision`/`manage_budget`, а M2-команды требуют их на
   пакете. В прогоне выданы прямой вставкой; в проде их должен выдавать
   invitation-поток.
4. **versionId package-wide** — предлагаю зафиксировать в контракте команды
   явным словом (сейчас это видно только по ошибке P1111).

## Границы прогона

- Клиентская витрина с тремя карточками (submit_m2_client_review) требует
  полной «шестой петли» контура (решения → выборки с ценами → approval →

  рендер панели закрыт их UI-тестами и моими статическими. Полный цикл
  витрины — часть их pilot-evidence, не дублировался.
- Актёрская модель прогона: дизайнер — пакетный architect с добавленными
  capabilities (находка №3), клиент — проектный client_approver.
