## 0. Две лестницы — и как они соотносятся

В проекте две разные лестницы, и путать их нельзя:

| Лестница | Про что | Ступени |
|---|---|---|
| **Позиционирование §7** (эта) | готовность продукта к аудитории | Ступень 1 «Пилот» → Ступень 2 «Расширение» → Ступень 3 «Публичный запуск» |
| Маркетплейс A→B→C | механика Входа Б | не предмет этого документа |

Настоящий документ определяет ровно одну границу: **Ступень 1 → Ступень 2**.
Она проходится, когда закрыты все четыре гейта S1–S4. Границу Ступень 2 → 3
держат гейты L1–L3 (юрблок, позиционирование, онбординг) — они здесь не
детализируются.

**Что открывает Ступень 2** (из позиционирования §7, это следствия, а не
гейты): лендинг v2, публикация SEO-страниц, кейсы пилота «выигранный спор»,
реферальная петля дизайнер → клиент в рамках ограничений Входа А/Б.

**Принцип границы** (принят 05.07.2026, не пересматривается здесь): переход —
**по завершении WTP-интервью**, не по числу бюро и не по календарю. S1 зависит
именно от выводов интервью, поэтому S1 — задающий гейт; S2–S4 могут закрываться
параллельно, но Ступень 2 не наступает раньше S1.

## 1. S1 — ценовое поведение КП решено по итогам WTP

**Смысл.** Гейт — не «цена обязана быть в КП», а «как КП показывает цену —
решено интервью, а не документом заранее». Гипотезы к интервью зафиксированы в
позиционировании §4: подписка за рабочее пространство студии; клиент бесплатно
всегда; без платы за места и за экспорт.

**Текущее состояние: DOC_TARGET.** WTP-артефактов в репозитории нет
(поиск `*wtp*` по `docs/` — пусто). Механизм «без цены» существует:
`designers.pricing = null` собирает КП без блока стоимости.

**Критерии прохождения — все обязательны:**

| # | Критерий | Доказательство |
|---|---|---|
| S1.1 | Проведено ≥5 WTP-интервью с дизайнерами/студиями пилота, каждое — про числа (готовность платить за конкретную модель из §4), не про концепцию | `docs/product-intelligence/wtp/WTP_INTERVIEW_<n>_<дата>.md` на каждое; PII интервьюируемых — только с их согласия, иначе обезличенно |
| S1.2 | Владелец подписал решение «как КП показывает цену» (варианты: диапазон всегда / по запросу дизайнера / режим без цены остаётся дефолтом / иное) | `REMHAOS_OWNER_DECISION_S1_PRICING_<дата>.md` + строка в Decision Log |
| S1.3 | Поведение КП приведено в соответствие решению S1.2 | тест на рендер блока стоимости по каждому режиму решения; ссылка `файл:строка` |
| S1.4 | Гипотезы цены из §4 подтверждены, опровергнуты или заменены — явным списком в решении S1.2 | тот же документ |

**Кто:** интервью и решение — владелец; S1.3 — исполнитель после решения.

## 2. S2 — rule-based risk engine реально срабатывает

**Смысл.** Юнит-уровень давно зелёный; вопрос гейта — срабатывает ли слой 1 на
живом пути (реальный intake → `risk_cards` в базе), и не прячет ли деградация
LLM rule-карточки.

**Текущее состояние: юнит — VERIFIED, живой путь — NOT_VERIFIED.**
9 детерминированных правил в `lib/risks/rules.ts:42` (`evaluateRules`),
покрыты `lib/risks/rules.test.ts` (правила 1–9 позитивно, плюс негативные случаи).
Свежего прогона на стенде с доказательством «карточки появились в базе» нет —
исторический вопрос «движок молчит всегда или был таймаут LLM» (CLAUDE.md, S2)
не закрыт прогоном.

**Критерии прохождения:**

| # | Критерий | Доказательство |
|---|---|---|
| S2.1 | Эталонный набор противоречивых брифов (минимум по одному на каждое из 9 правил) прогнан через реальный intake-путь на живом стенде; для каждого правила в `risk_cards` появилась карточка `source='rule'` | протокол прогона: project id → правило → id карточки; 9/9 |
| S2.2 | Контрольный непротиворечивый бриф даёт 0 rule-карточек | тот же протокол |
| S2.3 | При недоступном LLM-провайдере (таймаут/отказ) rule-карточки всё равно записываются — деградация не съедает слой 1 | прогон с заведомо сломанным `LLM_PROVIDER`; карточки `source='rule'` в базе |
| S2.4 | Эталонные брифы зафиксированы как fixtures в репозитории — прогон воспроизводим | `tests/fixtures/` или e2e-тест |

**Кто:** исполнитель; владелец принимает протокол.

## 3. S3 — завершение сделки в публичном КП

**Смысл.** Клиент должен уметь ответить на КП с публичной страницы, ответ —
видим дизайнеру и привязан к тому, на что клиент отвечал.

**Текущее состояние: CODE_PRESENT, без тестов, с двумя разрывами.**
Построено больше, чем помнит историческая формулировка 05.07: CTA
«Принять / Обсудить / Запросить правки» на `/p/[public_token]` есть
(`lib/proposal/respond.ts:4-10`); принятие ставит `proposals.status='accepted'`
и `projects.status='proposal_accepted'` (`app/api/proposal/respond/route.ts:61-63`);
кабинет показывает ответ (`app/dashboard/projects/[id]/proposal/page.tsx:130-163`);
повторный ответ идемпотентен — первый выигрывает (`route.ts:44-48`).
Разрывы: (а) явного «Отклонить» нет — только обсуждение/правки;
(б) ответ не привязан к версии КП — везде жёстко `.eq("version", 1)`
(снимается работой B2 Фазы 2); (в) юнит-тестов на respond-контур нет.

**Критерии прохождения:**

| # | Критерий | Доказательство |
|---|---|---|
| S3.1 | С публичной страницы доступны и записываются все ответы: принять / обсудить / запросить правки; решение о явном «Отклонить» принимает владелец (см. §6, вопрос 1) | тест на каждый тип ответа |
| S3.2 | Принятие фиксируется за конкретной версией КП: v1 отправлена → v2 создана → принята v2 → v1 осталась `sent` | тест из ТЗ Фазы 2 B2 |
| S3.3 | Повторный и конфликтующий ответы идемпотентны: первый записанный ответ выигрывает, повтор возвращает его же | тест |
| S3.4 | Дизайнер видит ответ и его время в кабинете без обращения к базе | тест или скриншот-протокол |
| S3.5 | Событийная цепочка полна: `proposal_sent` → `proposal_viewed` → ответное событие; каждое пишется ровно один раз | тест по `events` |

**Кто:** исполнитель (S3.2 — в составе B2 Фазы 2); владелец — вопрос §6.1.

## 4. S4 — петля обратной связи

**Смысл.** Дизайнер узнаёт о движении клиента сам, а не заглядывая в базу:
бриф заполнен → дизайнер уведомлён; КП открыто → дизайнеру видно.

**Текущее состояние: половина CODE_PRESENT, половина NOT_BUILT.**
Просмотр КП пишется — `proposal_viewed`, один раз на проект
(`app/p/[public_token]/page.tsx:55`), кабинет его показывает
(`proposal/page.tsx:161-163`). Уведомления дизайнеру о заполненном брифе НЕТ
ни по одному каналу: `app/api/intake/submit/route.ts` пишет событие
`brief_completed` (строка 74) и на этом останавливается. Telegram-мост
существует, но выключен и production не разрешён (DEC-031); email-канала нет —
выделенный SMTP не настроен (это же — предусловие Фазы 4).

**Критерии прохождения:**

| # | Критерий | Доказательство |
|---|---|---|
| S4.1 | При `brief_completed` дизайнер получает уведомление минимум по одному реальному каналу (email через выделенный SMTP — базовый вариант; Telegram — только если мост разрешён отдельным решением) | доставленное уведомление в тестовом прогоне на стенде |
| S4.2 | Уведомление не несёт PII клиента сверх необходимого: имя проекта/клиента — да; телефон, email, город клиента — нет | текст шаблона + тест |
| S4.3 | Отказ канала уведомлений не роняет и не откатывает submit брифа | тест: SMTP недоступен → бриф сохранён, событие есть |
| S4.4 | Кабинет показывает `proposal_viewed` и время без обращения к базе | уже построено — подтвердить тестом |
| S4.5 | Событие уведомления пишется в `events` (например `brief_notification_sent`) — петля наблюдаема | тест |

**Кто:** исполнитель; выбор канала и настройка SMTP — владелец (§6, вопрос 2).
