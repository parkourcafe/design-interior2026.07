## Наблюдение, из которого всё следует

Людей нельзя выселить из мессенджеров, и не нужно: клиенту удобно в чате,
проектные чаты будут всегда. Продукт, требующий «переезжайте к нам»,
проигрывает привычке. Значит, канал общения остаётся чужим — а вот **запись
решений** обязана становиться нашей. Поза: *чат — где говорят; RemHaOS — где
остаётся.*

Это не новый столп позиционирования, а механика первого («единая история»):
решения рождаются в переписке, и мост — то, что делает «записано» правдой, а
не благим пожеланием.

## MVP — два жеста, оба через Telegram-бота

1. **Переслать боту (личка).** Дизайнер пересылает сообщение из любого чата
   боту → бот спрашивает, к какому проекту отнести → сообщение становится
   фактом проекта. Пересланное сообщение сохраняет автора и время оригинала.
   Ноль настройки, ноль трения для клиента, работает с ЛЮБЫМ чатом — даже
   тем, где бота нет.
2. **Зафиксировать в группе.** Бот добавлен в чат проекта; ответ (reply) на
   сообщение с упоминанием бота фиксирует его как решение. Все участники
   видят, что зафиксировано — это честно и само по себе дисциплинирует.

Фото и документы — вложениями к факту; голосовые — транскрипция и текст как
факт с пометкой «расшифровка, не проверена».

## Почему это дёшево: всё ложится на существующее

- **Провенанс уже есть.** `project_facts.evidence_locator text not null`
  (миграция `0007_platform_foundation_m1.sql`, уникальность
  `(project_id, evidence_locator, version)`). Ссылка вида
  `telegram://chat/<id>/message/<id>` — ещё один вид локатора, ноль изменений
  схемы. Ревью фактов человеком уже построено (`fact-review.tsx`).
- **События уже есть** (`events`): `chat_message_ingested`,
  `chat_decision_pinned` — обычные строки.
- **Дисциплина неподтверждённости уже есть:** факт из чата рождается со
  статусом «требует подтверждения» — тот же human-gate, что у фактов из брифа.
  AI ничего не решает сам (ARCHITECTURE §14).
- Telegram Bot API бесплатен, без модерации, файлы до 20 МБ через `getFile`.

Новый код — только webhook-роут бота и маппинг сообщения в факт. Ни одной
новой top-level сущности.

## Границы и гейты (до разработки, обязательные)

1. **152-ФЗ / согласие.** Переписка — ПДн участников. Гейт: формулировка
   согласия в клиентском соглашении + правило маскирования при любом
   LLM-вызове (механика `lib/risks/llm.ts` уже есть). Юридическая проверка —
   как D-QC-09 в QC-драфте.
2. **Секретарь, не прослушка.** По умолчанию фиксация ТОЛЬКО явным жестом.
   Полное впитывание ленты группы — отдельный осознанный opt-in, видимый всем
   участникам чата. Продукт доверия не может начинаться со скрытого
   архивирования.
3. **Транскрипция голосовых** — только через действующего провайдера по env
   (та же политика, что LLM продукта); сторонние облака запрещены — тот же
   принцип, что запрет облачной конвертации DWG (A4 §3).
4. **WhatsApp Business API — не для контура РФ** (правовой статус Meta в РФ;
   канал РФ — Telegram). Для будущих рынков — отдельное решение. Появление
   новых мессенджеров (MAX) — наблюдаем, не строим.
5. **Правило обоснования функции (A4 §2.0): проходит.** Мост фиксирует
   решения там, где они рождаются; без него «записано» зависит от дисциплины
   ручного переноса, то есть не работает.

## Один мост — четыре модуля (уточнение владельца, 08.08)

Мост — горизонтальный слой ядра, как движок версий: строится один раз,
включается на любом модуле по мере его открытия. Механика везде одна —
сообщение → факт с происхождением → подтверждение человеком. Модуль
определяет только то, чем факт становится:

| Модуль | Что рождается в чате | Чем становится после подтверждения |
|---|---|---|
| M1 · Бриф и КП | уточнения клиента: бюджет, сроки, «это важно» | факт брифа / паспорта |
| M2 · Планировки | «берём вариант Б», «плитку такую, не дороже 3500» | отзыв клиента, согласование варианта, выбор материала |
| M3 · Документация | вопрос подрядчика к чертежу, ответ архитектора | RFI и решение по нему |
| M4 · Стройка и приёмка | фото работ, «переделали, смотрите» | наблюдение с площадки, кандидат в evidence |

Оговорка для M4, обязательная к сохранению: чат-фото попадает в проект как
**наблюдение**, но приёмка критических скрытых работ по фото из чата не
делается — для контрольных точек QC-драфт требует guided capture и
профессиональную проверку. Мост дополняет эту дисциплину, а не обходит её.

## Чего этот мост НЕ делает

- Не заменяет чат и не строит свой мессенджер.
- Не архивирует всю переписку по умолчанию.
- Не превращает сообщение в утверждённый факт без человека.
- Не входит в сдачу M2 и не открывает новый фронт до отдельного «строим».
