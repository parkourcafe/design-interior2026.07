## 1. Решение

### 1.1 Telegram — основной внешний канал рабочей переписки

Людей не выселить из мессенджеров, и не нужно. Канал общения остаётся чужим —
**запись решений** обязана становиться нашей.

### 1.2 RemHaOS остаётся системой официальных решений

RemHaOS — место, где живут полномочия, версии, изменения, доказательства и
официальные решения. Telegram — место, где говорят. Мост переносит **сырьё**,
а не полномочия.

### 1.3 Мост — один горизонтальный адаптер

Telegram Chat Bridge — адаптер в `Integration Gateway → Messaging`
(ARCHITECTURE §9). Он **не** Module 5 и **не** отдельный бот на каждый модуль
M1–M4. Один контур приёма, один контур отправки, доменные адаптеры сверху.

### 1.4 Объём P0

Поддерживается:

- один активный Telegram-чат на один проект;
- один проект на один активный Telegram-чат;
- постоянный приём новых сообщений после явного подключения;
- первый доменный адаптер **M3 → M4**;
- обратные уведомления RemHaOS → Telegram;
- защищённые переходы Telegram → RemHaOS.

### 1.5 Бот не создаёт человеческую группу

Telegram Bot API не позволяет боту создать обычную группу. Группу создаёт или
выбирает человек и добавляет бота через `startgroup`. В интерфейсе **запрещено**
обещать автоматическое создание чата. Точный текст действия:

> **Создать или подключить Telegram-чат**

### 1.6 Всё из чата — только кандидат

Сообщения, фото, документы и выводы AI создают **только неподтверждённые
кандидаты** в Project Inbox. Кандидат не является ни фактом проекта, ни
решением, ни изменением, ни доказательством.

### 1.7 Telegram не переносит полномочия

- членство в Telegram-группе не создаёт аккаунт или роль RemHaOS;
- сообщение «получил» не выполняет `acknowledge_release`;
- фото не является автоматически evidence или приёмкой;
- предложение о замене не является утверждённым изменением;
- Telegram callback или deep link не выполняет официальную mutation;
- официальное действие выполняется **только** существующей командой RemHaOS
  после входа и явного подтверждения человека.

### 1.8 Первый рабочий сценарий

```text
Released Production Package
  → distribute_release
  → уведомление в Telegram
  → защищённый переход в RemHaOS
  → acknowledge_release сессией получателя
  → сообщение строителя
  → change_request_candidate
  → проверка человеком
  → create_change
```

### 1.9 Мост выключен по умолчанию

`REMHAOS_TELEGRAM_BRIDGE_ENABLED=false`. Выключенный мост не принимает, не
классифицирует и не отправляет сообщения.

### 1.10 Отношение к Charter §12

A7 изменяет Charter §12 **только настолько**, чтобы разрешить разработку и
тестирование Telegram Bridge в local, CI и закрытом staging с тестовыми
участниками. Формулировка §12 «мессенджеры заблокированы» остаётся в силе для
продакшена и для реальной переписки третьих лиц.

A7 **НЕ** разрешает:

- production-включение;
- массовый приём реальной переписки третьих лиц;
- обход гейта российского data plane;
- считать вопрос 152-ФЗ закрытым;
- M4 Increment 2.

### 1.11 Production — отдельный OWNER GO

Production требует отдельного решения владельца после гейта
legal / data-plane / consent / retention. Уведомление в группе о сборе данных
не является юридическим закрытием 152-ФЗ.

### 1.12 Внутренний мессенджер не строится

Ни при каких обстоятельствах в этом P0 и после него без отдельного решения.

### 1.13 M1, M2 и прочие сценарии M3 в P0 не подключаются

Они требуют отдельного решения после первого пилота M3 → M4.

## 2. Целевая архитектура

Один горизонтальный контур приёма:

```text
Telegram
  → Telegram Transport Adapter
  → durable Channel Inbox
  → normalized Channel Event
  → extraction worker
  → Project Inbox Candidate
  → human review
  → существующая команда M1–M4
```

Обратный путь:

```text
domain event / persisted state
  → Notification Outbox
  → Telegram Sender
  → Telegram message
  → protected RemHaOS deep link
```

### 2.1 Запрещено (инварианты моста)

- писать Telegram-код отдельно в M1, M2, M3 и M4;
- добавлять `telegram_chat_id` или `telegram_user_id` в доменные таблицы
  модулей;
- напрямую писать из webhook в business tables M1–M4;
- вызывать human RPC через `service_role`;
- выполнять команды из текста сообщения;
- давать LLM tool-доступ к mutations;
- строить второй Project Memory или отдельную Telegram-истину.

### 2.2 Кодовый контур

- `lib/integration-gateway/telegram/**`;
- `app/api/integrations/telegram/**`;
- отдельные ports/adapters/runners по действующим архитектурным правилам;
- существующие command services RemHaOS остаются **единственным** официальным
  входом.

## 6. Два предположения гипотезы 08.08, которые больше не действуют

Гипотеза `CHAT_INGESTION_HYPOTHESIS_2026-08-08.md` остаётся источником
наблюдения и позиционирования, но два её технических предположения сняты:

1. **«Получение только явным упоминанием бота».** P0 поддерживает постоянный
   приём новых сообщений после явного подключения группы — с уведомлением всех
   участников до начала захвата. Причина: жест «упомяни бота» не переживает
   реальную стройку, где важное говорится мимоходом; а скрытого захвата не
   будет, потому что подключение явное и видимое.
2. **«Изменения схемы не нужны».** Гипотеза считала, что хватит
   `evidence_locator` и таблицы `events`. Это неверно: мосту нужны durable
   inbox, дедупликация `update_id`, ревизии отредактированных сообщений,
   карантин вложений, outbox с лизами и связь identity — то есть собственные
   таблицы. Без них «принято ровно один раз» и «ничего не потеряно при
   перезапуске» были бы обещанием, а не свойством.
