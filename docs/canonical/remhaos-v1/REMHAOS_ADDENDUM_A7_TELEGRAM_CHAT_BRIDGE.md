## 0. Главное, что владелец должен знать до подписи

1. **Мост — не модуль.** Telegram Chat Bridge живёт одним горизонтальным
   адаптером в `Integration Gateway → Messaging` (Architecture v1.1 §2, §9).
   Ни Module 5, ни «бот модуля 3», ни «бот модуля 4» не создаются. DEC-001
   («Module 5 не создаётся») остаётся в силе и этим документом подтверждается,
   а не обходится.

2. **Telegram становится основным внешним каналом рабочей переписки проекта,
   и это не делает его источником истины.** RemHaOS остаётся системой
   официальных решений, полномочий, версий, изменений и доказательств. Всё,
   что приходит из чата, рождается **кандидатом**, а не фактом.

3. **Бот не умеет создавать человеческие группы, и продукт не имеет права это
   обещать.** Telegram Bot API такой возможности не даёт: группу создаёт
   человек. Единственный честный жест — `?startgroup=<token>`, где Telegram сам
   предлагает пользователю **создать или выбрать** группу и добавить туда бота.
   Поэтому текст действия в интерфейсе — ровно `Создать или подключить
   Telegram-чат`, и ни одна формулировка не обещает автоматического создания.

4. **Мост не переносит полномочия.** Членство в Telegram-группе не создаёт
   аккаунт RemHaOS и не выдаёт роль. «Получил» в чате не является
   подтверждением получения выпуска. Фото из чата не является приёмкой.
   Официальное действие выполняет только существующая команда RemHaOS,
   человеческой сессией, после явного подтверждения человеком.

5. **Мост выключен по умолчанию** и не включается в production этой подписью.
   A7 разрешает разработку и испытания в local, CI и закрытом staging с
   **тестовыми участниками**. Production — отдельный OWNER GO после
   legal/data-plane/consent/retention гейта. Вопрос 152-ФЗ этим документом
   **не закрыт**.

6. **Объём P0 узкий намеренно:** один вертикальный сценарий M3 → M4. M1, M2 и
   остальные сценарии M3 требуют отдельного решения после первого пилота.

## 1. Что открывается

### 1.1 Один горизонтальный контур

Открывается постройка **одного** адаптера обмена сообщениями и его обвязки:

```text
Telegram
→ Telegram Transport Adapter
→ durable Channel Inbox
→ normalized Channel Event
→ extraction worker
→ Project Inbox Candidate
→ human review
→ существующая команда M1–M4
```

Обратный путь:

```text
domain event / persisted state
→ Notification Outbox
→ Telegram Sender
→ Telegram message
→ protected RemHaOS deep link
```

### 1.2 Что поддерживает P0

1. Один активный Telegram-чат на один проект.
2. Один проект на один активный Telegram-чат.
3. Постоянный приём новых сообщений после явного подключения.
4. Первый доменный адаптер — M3 → M4.
5. Обратные уведомления RemHaOS → Telegram.
6. Защищённые переходы Telegram → RemHaOS.

### 1.3 Первый рабочий сценарий

```text
Released Production Package
→ distribute_release
→ уведомление в Telegram
→ защищённый переход в RemHaOS
→ acknowledge_release сессией получателя
→ сообщение строителя
→ change_request_candidate
→ проверка человеком
→ create_change
```

Сценарий выбран не по вкусу: это единственный участок, где инкремент 1 модуля 4
уже доказан браузером (`M4_BROWSER_PROVEN`, DEC-029) и где у моста есть и
исходящая, и входящая половина в одном проекте.

### 1.4 Что остаётся закрытым

- M1, M2 и любые другие сценарии M3 — отдельным решением после первого пилота;
- M4 Increment 2 — **не открывается** ничем в этом документе;
- собственный мессенджер RemHaOS — не строится (подтверждение, не новация);
- любые каналы, кроме Telegram.

## 2. Архитектурное место моста

По Architecture v1.1 §2 мост принадлежит `INTEGRATION GATEWAY → Messaging`.
Из этого следуют запреты, которые действуют с даты подписи:

1. **Нельзя писать Telegram-код в M1, M2, M3 и M4.** Доменные модули не знают о
   существовании Telegram. Они знают о Project Inbox Candidate и о Notification
   Outbox — и то, и другое нейтрально к каналу.
2. **Нельзя добавлять `telegram_chat_id` или `telegram_user_id` в доменные
   таблицы модулей.** Внешние идентификаторы живут только в таблицах шлюза.
3. **Нельзя писать из webhook напрямую в business tables M1–M4.**
4. **Нельзя звать человеческие RPC под `service_role`** (AGENTS.md: «Human
   operations не выполняются через service role»).
5. **Нельзя исполнять команды из текста сообщения.**
6. **Нельзя давать LLM tool-доступ к мутациям.** AI возвращает структуру и
   ничего не вызывает (Architecture §14, DEC-008).
7. **Нельзя строить вторую Project Memory или отдельную «телеграм-истину»**
   (DEC-002).

Кодовый контур — `lib/integration-gateway/telegram/**` и
`app/api/integrations/telegram/**`. Существующие command services RemHaOS
остаются единственным официальным входом.

---

## 3. Мост не переносит полномочия

Это отдельный раздел, а не пункт в списке, потому что здесь ошибиться дороже
всего.

| Что происходит в Telegram | Что это НЕ делает в RemHaOS |
|---|---|
| человек состоит в группе проекта | не создаёт аккаунт и не выдаёт роль |
| человек пишет «получил, всё вижу» | не выполняет `acknowledge_release` |
| человек прислал фото работ | не создаёт evidence и не выполняет приёмку |
| человек предложил замену материала | не создаёт утверждённое изменение |
| человек нажал inline-кнопку бота | не выполняет официальную mutation |
| человек открыл deep link | не подтверждает ничего: GET не мутирует |

Официальное действие выполняется **только** существующей командой RemHaOS,
после входа, человеческой сессией и отдельным явным подтверждением. Сервер
заново выводит actor, organization, project, package, role и effective scope —
как для любого другого запроса (AGENTS.md, неподвижные правила).

---

## 4. Кандидаты, а не факты

Сообщения, фото, документы и AI-выводы создают **только неподтверждённых
кандидатов** в Project Inbox. Кандидат:

- несёт источник (`channel_event`), провенанс и версию схемы извлечения;
- живёт в статусах `pending` / `confirmed` / `rejected` / `superseded`;
- не превращается в официальный объект без человеческой команды;
- фиксирует, кто и когда его проверил, по серверному времени.

Минимальные типы P0: `question`, `decision_candidate`, `change_request_candidate`,
`risk_candidate`, `general_note`, `ignored`.

Это та же дисциплина неподтверждённости, что у фактов из брифа и у любого
AI-вывода (Charter safety, DEC-008). Мост её не ослабляет.

## 5. Подключение чата — что можно обещать пользователю

### 5.1 Жест

Бот не может сам создать человеческую группу. Пользователь создаёт или выбирает
группу и добавляет туда бота через `?startgroup=<token>`. Точный текст действия
в интерфейсе:

> `Создать или подключить Telegram-чат`

Формулировки вида «мы создадим чат проекта» запрещены: они обещают то, чего
Bot API не даёт.

### 5.2 Порядок

1. Авторизованный владелец проекта связывает свой Telegram-аккаунт с RemHaOS
   через приватный deep link бота и одноразовый intent.
2. Только после верифицированной identity RemHaOS создаёт binding intent.
3. Открывается `https://t.me/<bot_username>?startgroup=<opaque_token>`.
4. Telegram предлагает создать или выбрать группу и добавить бота.
5. Сервер, получив `/start@bot <token>`, проверяет: токен, TTL, одноразовость,
   связанного Telegram-пользователя, project membership, capability
   `manage_project_integrations`, администраторство инициатора **в выбранной
   группе** и то, что чат не связан с другим проектом.
6. Privacy mode бота остаётся включённым глобально. Полный приём переписки
   существует только там, где пользователь сам сделал бота администратором
   проектной группы с минимально необходимыми правами.

### 5.3 Уведомление участников

До начала полного захвата бот публикует в группе понятное уведомление: что
новые сообщения и вложения передаются в RemHaOS; что AI может искать вопросы,
решения, риски и изменения; что официальные решения требуют подтверждения в
RemHaOS; как остановить сбор; и что история до подключения не импортируется.
Если права позволяют — уведомление закрепляется.

**Одно уведомление не закрывает 152-ФЗ.** Это продуктовая честность, а не
юридическое основание. Юридическое основание — отдельный production-гейт (§9).

### 5.4 Деградация

- бот удалён или понижен в правах → binding переходит в `suspended`;
- бот добавлен в несвязанную группу → содержимое не сохраняется, бот сообщает,
  что подключение не завершено;
- миграция группы в супергруппу → перепривязка либо безопасный
  `suspended` / `needs_rebind`.

## 6. Гарантия доставки

Telegram `sendMessage` не принимает внешний ключ идемпотентности. Поэтому
гарантия называется прямо:

> **at-least-once delivery + внутренняя дедупликация.**

Exactly-once отправка **не обещается**. После неопределённого сетевого
результата редкий повтор уведомления допустим; повтор бизнес-действия —
нет. Разница принципиальная: уведомление — это текст, а действие — это команда,
и вторая половина защищена идемпотентностью существующих командных RPC.

Симметрично на входе: повтор `update_id` создаёт **один** event.
`edited_message` создаёт **новую ревизию источника** — он не переписывает старую
запись и не изменяет уже подтверждённый официальный объект. Синхронизация
удалений **не обещается**: обычный бот не получает надёжных событий обо всех
удалённых сообщениях.

## 7. Безопасность и доступ

1. Технические таблицы моста закрыты от `anon` и от прямой записи
   `authenticated`; RLS deny-by-default.
2. Входящий путь пишет только минимальный системный адаптер.
3. Человеческий review идёт через authenticated request-bound route/команду.
4. Bot token и webhook secret не попадают в базу и не пишутся в логи.
5. У моста своя surface/access matrix — по тому же уроку, что дали guardrail'ы
   M3 и M4: границу нельзя проверять по имени схемы.
6. `REMHAOS_TELEGRAM_BRIDGE_ENABLED=false` по умолчанию. Выключенный мост не
   принимает, не классифицирует и не отправляет сообщения.
7. Ни строки исходного текста переписки, ни имени файла, ни download URL, ни
   токена — в structured logs (AGENTS.md, правило про AI и логи).

### 7.1 Новая capability

Вводится `manage_project_integrations` в существующем реестре capability
(`projectceo_foundation._role_capabilities`), **без второго списка ролей рядом**.
В P0 она выдаётся только project-scoped `owner_lead` — каноническому владельцу
проекта. Package-scoped роли её не получают.

Это же снимает риск, записанный пунктом 6 backlog `M4 Production Hardening`
(«роли выдачи в приложении перечислены, а не выведены»): новый слой обязан
спрашивать capability, а не сравнивать строку роли.

## 8. Инварианты A7

Действуют с даты подписи и проверяются кодом, а не глазами.

- **INV-T1.** Один активный Telegram-чат на проект и один проект на активный
  чат. Ограничение серверное; конкурентные подключения его не обходят.
- **INV-T2.** Связь Telegram-аккаунта с RemHaOS строится **только** по
  стабильному числовому Telegram user ID. Никогда — по username, телефону или
  отображаемому имени. Смена username связь не рвёт.
- **INV-T3.** Telegram-связь не создаёт project membership и не выдаёт
  capability.
- **INV-T4.** Всё, что пришло из чата, рождается кандидатом. Официальным
  объектом кандидат становится только человеческой командой.
- **INV-T5.** Токены подключения и связывания: криптослучайный nonce, в базе
  только hash, TTL 10 минут, одноразовость, отзыв, привязка к
  actor/project/purpose. Токен не содержит project ID, organization ID и
  чувствительных данных и помещается в лимит Telegram `start` / `startgroup`.
- **INV-T6.** Выключенный мост — no-op или контролируемый отказ **до** любых
  бизнес-чтений.
- **INV-T7.** Ни одна доменная таблица M1–M4 не получает поля с внешними
  идентификаторами Telegram.
- **INV-T8.** LLM в контуре моста не имеет tools и не может вызвать mutation;
  он обязан уметь вернуть `ignored`.
- **INV-T9.** A7 не добавляет новых провайдеров LLM: используется существующая
  абстракция `lib/llm/provider.ts` и существующая политика измерения стоимости.
- **INV-T10.** Deep link — обычная защищённая web-ссылка. GET ничего не
  подтверждает.

## 9. Что A7 правит в Charter §12 — и что не правит

Charter v0.5 §12 держит потолок P0 и прямо перечисляет мессенджеры среди
заблокированного до закрытия гейта российского data plane и 152-ФЗ.

**A7 правит §12 ровно настолько:** разрешает **разработку и тестирование**
Telegram Bridge в local, CI и **закрытом staging с тестовыми участниками**.

**A7 НЕ разрешает:**

1. production-включение;
2. массовый приём реальной переписки третьих лиц;
3. обход российского data-plane гейта;
4. считать вопрос 152-ФЗ закрытым;
5. M4 Increment 2.

Production требует **отдельного OWNER GO** после legal / data-plane / consent /
retention гейта. DEC-014 («Integration order не является разрешением»)
сохраняется: место Telegram в порядке интеграций Architecture §9 по-прежнему
ничего не открывает само по себе.

называется `TG4_BLOCKED_EXTERNAL_CREDENTIALS`.

Цикл 7 (внешний реальный пакет) остаётся открытым и красным. A7 его не
закрывает и не притворяется, что закрывает.

## 11. Отношение к гипотезе чат-моста от 08.08.2026

`docs/positioning/CHAT_INGESTION_HYPOTHESIS_2026-08-08.md` помечается как
**PARTIALLY SUPERSEDED BY A7 / DEC-031**. Исторический текст не переписывается.

**Что из неё больше не действует:**

1. **«Получение только явным упоминанием бота».** P0 A7 — постоянный приём
   новых сообщений после явного подключения группы и уведомления участников.
   Жест «упомяни бота» перестал быть механизмом захвата.
2. **«Изменения схемы не нужны».** Неверно. Мосту нужны собственные таблицы:
   привязки, связи identity, интенты, события канала, вложения, кандидаты и
   outbox. Провенанс через `evidence_locator` — не замена durable inbox.

**Что из неё сохраняется:** поза «чат — где говорят; RemHaOS — где остаётся»;
один мост на четыре модуля; кандидат подтверждается человеком; фото из чата не
делает приёмку скрытых работ; WhatsApp вне контура РФ.

## 12. Что не строится (Non-goals P0)

Собственный мессенджер · автоматическое создание Telegram-группы · импорт старой
переписки · синхронизация удалений · несколько чатов одного проекта · отдельные
проекты по Telegram topics · WhatsApp, MAX, Slack и другие каналы ·
автоматическое превращение участников чата в пользователей RemHaOS · approvals
и официальные действия через inline callback · полноценный Telegram Mini App ·
голосовая транскрипция · OCR и обработка видео · файлы больше 20 МБ через Bot
API · отправка пакетов и документов в группу · адаптеры всех четырёх модулей ·
production entitlement · M4 Increment 2 · новый универсальный worker framework.

Переходы — обычные защищённые web deep links.

Если Mini App появится позже, отдельное обязательное требование: серверная
проверка подписи `Telegram.WebApp.initData` и свежести `auth_date`.
`initDataUnsafe`, `start_param` и `chat_instance` авторизацией **не являются**.
