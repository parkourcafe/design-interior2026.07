### Почему TG1 и TG2 переоткрыты

Дефекты найдены в уже слитом коде (#84, #87, #89) и перечислены здесь, чтобы их
нельзя было потерять:

1. уникальность активной связи включает `bot_instance_id`, поэтому один чат
   можно связать с двумя проектами через двух ботов;
2. приём начинается до публикации уведомления участникам: связь создаётся сразу
   `active`, а уведомление отправляется после и ничего не блокирует;
3. при активации не перепроверяются project membership, capability и
   администраторство самого бота;
4. конфликт связи аккаунтов гасится `on conflict do nothing` и отдаётся как
   успех;
5. очередь уведомлений не возвращает в работу протухшую аренду `sending`, а
   `mark sent/failed` не проверяет ни аренду, ни терминальность `cancelled` —
   отменённое уведомление можно воскресить;
6. ревизия правки вычисляется через `max(...)+1` без блокировки, поэтому третья
   и последующие правки теряются, а вызов при этом отвечает «сохранено».

## 1. Что нужно, чтобы мост вообще ожил

Мост закрыт двумя независимыми границами. Обе обязаны быть открыты; открытие
одной ничего не даёт.

| Граница | Чем закрыта | Как открыть |
|---|---|---|
| Приложение | `REMHAOS_TELEGRAM_BRIDGE_ENABLED` | ровно строка `true` |
| База | системные RPC выданы только `service_role` | не открывается — так и задумано |

Вторая строка не опечатка. Человеческая сессия не достаёт до приёма сообщений
и очереди ни при каком значении флага: у роли `authenticated` нет прав на эти
функции. Флаг закрывает применение, база — доступ.

### Переменные окружения

```
REMHAOS_TELEGRAM_BRIDGE_ENABLED=false   # по умолчанию выключено
TELEGRAM_TEST_BOT_TOKEN=                # токен бота @BotFather
TELEGRAM_TEST_WEBHOOK_SECRET=           # ≥32 случайных символа
TELEGRAM_TEST_BOT_USERNAME=             # username бота без @
TELEGRAM_TEST_CHAT_ID=                  # только для гейта TG4
```

**Секреты не коммитятся.** Токен бота и секрет webhook'а не попадают в базу —
для них там нет колонки, и это свойство схемы, а не договорённость. В
структурные логи они не попадают тоже: событие лога принимает закрытый список
полей известных типов, и произвольный объект в него не передать.

Имена содержат `TEST_` намеренно. Пока production не разрешён отдельным
решением, у продовых имён нет повода существовать: завести
`TELEGRAM_BOT_TOKEN` значило бы заранее приготовить продовый слот.

## 2. Регистрация webhook

Один раз на окружение, из терминала оператора:

```bash
curl -sS "https://api.telegram.org/bot${TELEGRAM_TEST_BOT_TOKEN}/setWebhook" \
  -d "url=https://<host>/api/integrations/telegram/webhook" \
  -d "secret_token=${TELEGRAM_TEST_WEBHOOK_SECRET}" \
  -d "allowed_updates=[\"message\",\"edited_message\",\"my_chat_member\"]"
```

`secret_token` обязателен. URL webhook'а знает всякий, кто его однажды видел, а
тела запросов Telegram не подписывает — заголовок
`X-Telegram-Bot-Api-Secret-Token` и есть единственное доказательство
отправителя. Сравнение на нашей стороне постоянного времени.

`allowed_updates` сужен намеренно: чего мост не обрабатывает, того он и не
должен получать.

Снять webhook: `deleteWebhook`. Проверить: `getWebhookInfo` — в ответе не
должно быть `last_error_message`.

> **Внимание.** Команда содержит токен в URL. Не вставлять её в тикеты, чаты и
> логи CI. То же правило действует для `getFile`: возвращаемый им путь
> скачивания подставляется в URL с токеном, и этот URL нигде не хранится.

## 3. Подключение чата к проекту

Порядок обязателен: сначала личность, потом группа. Иначе непонятно, чьё
«добавил бота» мы приняли.

1. **Шаг 1 — связать аккаунт.** Владелец проекта открывает вкладку
   «Участники» → «Связать мой Telegram-аккаунт» → переходит по ссылке →
   «Запустить». Бот получает `/start <nonce>` в личном чате.
2. **Шаг 2 — подключить чат.** «Создать или подключить Telegram-чат» → Telegram
   предлагает выбрать группу → бот добавляется в неё.
3. Бот публикует в группе уведомление о сборе данных.

Ссылка живёт 10 минут и срабатывает один раз. В базе хранится только её
sha256 — утечка дампа рабочей ссылки не даёт.

### Что делать, если после добавления бота ничего не произошло

Экран показывает запасную команду вида `/start <nonce>`. Отправьте её в группу
текстом — подключение пройдёт тем же путём.

**Это не костыль на всякий случай, а следствие честного незнания.** Доставляет
ли Telegram `/start` с payload в саму группу при переходе по `?startgroup=`,
на этом этапе не проверено: для проверки нужен настоящий бот и настоящая
группа, то есть гейт TG4. Транспорт поэтому не полагается на автоматику и
принимает `/start <nonce>` из группы, откуда бы он ни пришёл. Если TG4
подтвердит автоматическую доставку, запасной путь останется безвредным.

### Ограничения, которые не обходятся

- один активный чат на проект и один проект на чат — частичные уникальные
  индексы в базе, а не проверка в интерфейсе;
- подключить чат может только **администратор группы** (проверяется через
  `getChatMember` до вызова базы) и только владелец проекта (capability
  `manage_project_integrations`);
- бот **не может создать группу** — Bot API этого не позволяет. Поэтому
  действие называется «Создать или подключить Telegram-чат»: человек создаёт
  чат сам.

## 4. Отправка уведомлений

```bash
npm run bridge:telegram-notifications
```

Один проход по очереди: забирает готовые записи, отправляет, отмечает
результат. Без `REMHAOS_TELEGRAM_BRIDGE_ENABLED=true` отказывается работать —
иначе он был бы обходом флага, а не его частью.

**Доставка at-least-once, не exactly-once.** Telegram `sendMessage` не
принимает внешний ключ идемпотентности, поэтому «ровно один раз» здесь
недостижимо в принципе. Что сделано: запись ставится в очередь один раз на
доменный факт (дедупликация в базе), захват идёт лизой, а не удалением, и
потерянный ответ приводит к повтору, а не к тишине. В худшем случае человек
увидит сообщение дважды — это заметно лучше, чем не увидеть ни разу.

### Разбор состояний очереди

| Состояние | Что значит | Что делать |
|---|---|---|
| `pending` | ждёт первой отправки | ничего |
| `sending` | захвачено, лиза не истекла | ничего; после истечения подберёт следующий прогон |
| `retry` | временный отказ | ничего; `next_attempt_at` назовёт срок |
| `sent` | доставлено | — |
| `failed` | постоянный отказ | смотреть `failure_code` |
| `cancelled` | связь отозвана или приостановлена | — |

Коды отказов санитизированы: `tg_403` (бота выкинули из группы — не
ретраится), `tg_429` (лимит частоты; пауза берётся из ответа Telegram),
`timeout`, `network`, `template_unknown`. Текст ошибки провайдера наружу не
идёт: он может содержать кусок отправленного сообщения.

## 5. Разбор входящего и Project Inbox

```bash
npm run bridge:telegram-workers
```

Один проход по двум очередям: проектор ставит в очередь уведомления о выдачах
M4, которых там ещё нет, а разборщик превращает сообщения чата в кандидатов
Project Inbox. Оба отказываются работать при выключенном флаге.

**Проектор читает состояние, а не перехватывает команду.** `distribute_release`
о существовании моста не знает — A7 §2.1 запрещает Telegram-код внутри модулей.
Побочное следствие важнее принципа: врезка в команду теряла бы уведомление при
падении между записью выдачи и постановкой в очередь, а «каких выдач ещё нет в
очереди» такого окна не имеет вовсе.

**Классификатор детерминированный, без LLM.** Правила узкие намеренно:
классификатор, который на всё отвечает «предложение», превращает Inbox в
свалку, человек перестаёт его читать, и граница «предложено ≠ утверждено»
рушится не запретом, а усталостью. `origin` у таких карточек — `rule`.

### Что видит человек

Вкладка «Изменения» → блок «Из чата проекта». Рассматривать кандидатов может
тот, у кого есть `review_source` (дизайнер проекта и архитектор; строитель и
заказчик — нет).

**Кнопка «Принять в работу» ничего не создаёт.** Она отмечает карточку
рассмотренной. Изменение, приёмку или решение создаёт отдельная команда
модуля, и порядок именно такой: сначала команда, потом отметка со ссылкой —
иначе ссылка указывала бы на несуществующее. Решение по карточке принимается
один раз: переголосование задним числом сделало бы аудит рассказом, а не
записью.

### Разбор состояний события

| Состояние | Что значит |
|---|---|
| `pending` | ждёт разбора |
| `processing` | захвачено, лиза не истекла |
| `processed` | кандидат создан |
| `ignored` | предлагать нечего («ок», стикер) |
| `dead_letter` | пять неудачных попыток; строка остаётся видимой |

## 6. Отключение и аварийная остановка

| Задача | Действие |
|---|---|
| Отключить один проект | «Отключить чат» на вкладке «Участники» |
| Остановить мост целиком | `REMHAOS_TELEGRAM_BRIDGE_ENABLED=false` + перезапуск |
| Прекратить приём на уровне Telegram | `deleteWebhook` |

Отключение проекта отзывает связь и отменяет невыполненные уведомления;
отключённый канал новых сообщений не принимает. Удаление бота из группы
приостанавливает связь автоматически — слать в чат, где бота нет, значит
держать очередь занятой навсегда.

При выключенном флаге маршрут webhook отвечает `404`. Telegram будет копить
обновления и повторять доставку — это ожидаемо; чтобы он перестал, снимите
webhook.

## 7. Чего мост не делает

Ни при каких настройках из этого документа:

- не создаёт официальных объектов домена. Всё из чата — **кандидат** в Project
  Inbox, и решением, изменением, приёмкой или доказательством не является;
- не исполняет команды из текста сообщения. Единственное, что мост читает в
  тексте, — одноразовый nonce рукопожатия, и полномочия даёт не текст, а
  запись намерения, созданная владельцем в интерфейсе RemHaOS;
- не переносит полномочия: членство в группе не создаёт аккаунт и роль,
  «получил» в чате не выполняет `acknowledge_release`, фото не становится
  evidence;
- не пишет в таблицы модулей M1–M4 и не хранит `telegram_chat_id` в них;
- не включает M4 в production и не открывает Increment 2.

Уведомление в группе о сборе данных **не является юридическим закрытием
152-ФЗ** (A7 §1.11).

## 8. Что блокирует гейт TG4

TG4 — «настоящий бот, настоящая группа, настоящий webhook». Он требует
`TELEGRAM_TEST_BOT_TOKEN`, `TELEGRAM_TEST_WEBHOOK_SECRET`,
`TELEGRAM_TEST_BOT_USERNAME` и тестовую группу (`TELEGRAM_TEST_CHAT_ID`).

Отсутствие этих данных блокирует **только TG4** и не блокирует TG0–TG3
(A7 §3). Пока их нет, статус этапа — `TG4_BLOCKED_EXTERNAL_CREDENTIALS`;
формулировка «staging proven» до реального прогона не применяется.

Что именно TG4 обязан подтвердить, потому что офлайн это подтвердить нечем:

1. доставляет ли `?startgroup=` команду `/start` с payload в группу;
2. приходит ли `my_chat_member` при удалении бота из группы;
3. форму `getChatMember` для создателя и администратора реальной супергруппы.
