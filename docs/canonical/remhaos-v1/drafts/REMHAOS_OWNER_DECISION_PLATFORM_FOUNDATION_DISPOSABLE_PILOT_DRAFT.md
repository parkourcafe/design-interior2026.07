## 0. Что этот документ закрывает

`PLATFORM_FOUNDATION = BLOCKED` появился в
`AP1_MIGRATION_PATH_DECISION_2026-08-01.md` и с тех пор упоминается в семи
местах канона как предусловие, которое «снимается отдельной записью владельца».
Записи не существовало. Из-за этого один флаг одновременно означал две разные
вещи:

1. **запрет на production adoption** — принять legacy baseline в журнал
   миграций живой базы можно только после отдельного reconciliation PR со
   снапшотом, сверкой отпечатков, упорядоченным replay и доказательством
   отката;
2. **запрет на платформенный фундамент в репозитории** — `project_facts`,
   `ai_calls`, Action/Skill Registry и переиспользуемый Approval gate нельзя
   было начинать, потому что A6 §7 и DEC-025 ссылались на тот же флаг.

Второе никогда не требовало первого. Настоящее решение разделяет их и снимает
ровно второе.

## 1. Решение

`PLATFORM_FOUNDATION` переходит из `BLOCKED` в
**`ACTIVE_FOR_DISPOSABLE_PILOT`**.

Это разрешает: строить платформенный фундамент в репозитории и доказывать его
на disposable-стенде и в CI.

Это НЕ разрешает и не приближает:

| Что остаётся закрытым | Чем закрыто |
|---|---|
| Production adoption legacy baseline | acceptance gate в `AP1_MIGRATION_PATH_DECISION_2026-08-01.md` — reconciliation PR не существует |
| Любое обращение к production Supabase `ztnycrchwxqczqbyegnp` | AGENTS.md; сессии исполнителей не имеют и не должны иметь доступа |
| `M4_PRODUCTION_ENABLED` | DEC-025, DEC-033 — отдельное решение владельца поверх этого |
| V2/V3 модуля 4 | DEC-032 — NOT AUTHORIZED до собственного M4 IMPLEMENTATION GO |
| DEC-026 / DEC-027 | Фаза 3 плана запуска |
| `PRODUCTION_READY = true` | AP1_RUNBOOK.md §5 — adoption checklist, snapshot, backup/restore rehearsal, SMTP/Auth/Storage, monitoring, отдельный человеческий GO |

Формулировка выбрана буквально: `ACTIVE_FOR_DISPOSABLE_PILOT`, а не `ACTIVE`.
Снять оставшуюся половину флага можно только тем самым reconciliation PR.

## 2. Предпосылки — проверяются на момент подписания

Владелец подписывает этот документ, только если все пять верны. Если хоть одна
не выполнена — документ не подписывается, а возвращается исполнителю.

| # | Предпосылка | Чем доказывается |
|---|---|---|
| 1 | Прогон AP1/AP5 на hosted disposable-стенде выполнен, звенья 1–15 пройдены отдельными ролевыми сессиями | `docs/audits/REMHAOS_AP1_PILOT_EVIDENCE_<дата>.md` |
| 2 | Стенд воспроизводится скриптом, без ручных правок | `tests/ap1/environment/bootstrap-disposable.zsh bootstrap` → `AP1_BOOTSTRAP_OK` |
| 3 | Журнал миграций стенда совпадает с ledger репозитория | `AP1_MIGRATION_LEDGER_FILE_OK` + `AP1_MIGRATION_LEDGER_DB_OK`, одинаковый count |
| 4 | Blocker `92060e3` (SECURITY DEFINER + `auth.uid()` от `pi_table_owner`) на managed Supabase текущего тарифа воспроизведён или опровергнут, вывод записан | раздел «Блокер `92060e3`» отчёта прогона; `AP1_DB_OK … managed_auth_references=0` |

Предпосылка 5 существует отдельно от 4 по прямому указанию AP1_RUNBOOK.md §6:

проверка шла с заплаткой. Зелёный прогон с заплаткой доказывает заплатку.
