# Удаление аккаунта дизайнера: 90 дней только для чтения — дизайн

Статус: **DESIGN + частичная реализация**.
Основание:
- DEC-040: 90 дней read-only и полного экспорта;
- DEC-041 §2: удаление аккаунта входит в этот срок, затем удаление ПДн;
- DEC-044 (a): в эти 90 дней вход только для чтения.

Реальное удаление данных (purge) **не разрешено** и не реализуется. Здесь описано, каким оно обязано быть, когда владелец его разрешит.

## 1. Что было до 28.09.2026

Маршрут `app/api/account/delete` сразу:
- стирал КП, ответы брифа, риски, комнаты и файлы;
- обнулял проекты и профиль;
- закрывал вход.

Проблемы:
- клиент мгновенно терял выданное и принятое КП;
- все версии паспорта клиента с контактами оставались в неизменяемой истории навсегда;
- договоры и события не удалялись;
- не было аудита, идемпотентности, отмены, legal hold и экспорта;
- шаги шли отдельными запросами без транзакции, поэтому сбой оставлял данные наполовину стёртыми.

## 2. Машина состояний заявки

```
(нет заявки) ──request──▶ requested ──cancel (до срока, без hold)──▶ cancelled
                              │
                              └── purge_after наступил, нет hold, нет архива ──▶ purge_eligible (вычисляется)
                                                                                     │
                                                                purge (НЕ реализован) ▼
                                                                                   purged
```

- `requested`:
  - дизайнер входит, видит проекты, скачивает полный экспорт и может отменить удаление;
  - изменять ничего нельзя: ни проекты, ни ответы, ни КП, ни договоры, ни комнаты;
  - клиенты открывают КП по ссылке, но не могут на них ответить;
  - бриф по ссылке тоже не принимается.
- `purge_after = requested_at + 90 дней`.
- `legal_hold` и `paid_archive_until` — атрибуты заявки. Их ставит оператор через серверную функцию.
  - Legal hold запрещает и отмену дизайнером, и purge.
  - Платный архив до даты запрещает purge.
- `cancelled` — терминальный статус. Новая заявка — новая строка.
- `purge_eligible` не хранится, а вычисляется: `plan_account_purge` считает его на момент запроса.
- `purged` зарезервирован за будущим разрешённым процессом.

## 3. Scope purge (для будущего процесса; сейчас только dry-run)

`plan_account_purge(designer_id)` возвращает без изменений данных:
- **блокеры:** срок не вышел, legal hold, платный архив, нет активной заявки;
- **счётчики:** проекты, КП, ответы, риски, комнаты, версии паспорта, договоры;
- **префиксы хранилища:** `client-uploads/{projectId}/`, `client-uploads/designer-plans/{projectId}/` и файлы договоров.

Будущий purge обязан:
1. Выполняться одной серверной транзакцией на проект. Повтор после сбоя продолжает с того же места (идемпотентность по `case_id` + проект). Каждый шаг записывается в `account_retention_events`.
2. Удалять версии паспорта через отдельную защищённую дверь с журналом. Сейчас триггер неизменяемости запрещает это всем, и это правильно: обойти его можно только осознанным решением.
3. Для проектов, подключённых к ProjectCEO (`project_workflows` с ON DELETE RESTRICT), не удалять каркас проекта, а обезличивать его. Неизменяемый аудит ProjectCEO хранит только идентификаторы.
4. Перепроверять hold и архив непосредственно перед каждым шагом.
5. Никогда не запускаться автоматически по таймеру без отдельного решения владельца (DEC-041 §2).

## 4. Аудит и идемпотентность

- `account_retention_events` — append-only журнал: `requested`, `replayed`, `cancelled`, `legal_hold_set`, `legal_hold_cleared`, `paid_archive_set`, `purge_planned`. В каждой записи автор и причина.
- Повторный запрос при активной заявке возвращает ту же заявку, а не создаёт новую.
- Отмена после срока или при hold отклоняется с понятной причиной.

## 5. Чтение и экспорт

- Полный экспорт `export_account_data()` доступен дизайнеру всегда, а не только в срок. В нём:
  - проекты без токенов доступа;
  - ответы брифа, риски;
  - все версии паспорта;
  - КП без публичной ссылки;
  - метаданные договоров и события.
- Файлы в экспорт пока не входят: экспорт перечисляет только их пути. Архив файлов — отдельная задача.

## 6. Что сознательно не сделано

- Нет purge-процесса и нет автоматического удаления по сроку.
- Нет интерфейса оператора для legal hold: есть только серверная функция с правом `service_role`.
- Уже удалённые до этого изменения данные не восстанавливаются. Задним числом ничего не удаляется.
