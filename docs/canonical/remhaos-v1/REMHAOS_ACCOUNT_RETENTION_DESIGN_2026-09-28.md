# Удаление аккаунта дизайнера: 90 дней только для чтения — дизайн

Статус: **DESIGN + частичная реализация**.
Основание:
- DEC-040: 90 дней read-only и полного экспорта;
- DEC-041 §2: удаление аккаунта входит в этот срок, затем удаление ПДн;
- DEC-044 (a): в эти 90 дней вход только для чтения;
- DEC-045 (a): после 90 дней — «срок вышел, ждёт удаления», вход закрыт, оператор может восстановить аккаунт.

Реальное удаление данных (purge) **не разрешено** и не реализуется. Здесь описано, каким оно обязано быть, когда владелец его разрешит.

## 1. Что было до 28.09.2026

Маршрут `app/api/account/delete` сразу:
- стирал КП, ответы брифа, риски, комнаты и файлы;
- обнулял проекты и профиль;
- закрывал вход.

Проблемы:
- клиент мгновенно терял выданное и принятое КП;
- все версии паспорта клиента с контактами оставались в неизменяемой истории навсегда;
- договоры и события не удалялись;
- не было аудита, идемпотентности, отмены, legal hold и экспорта;
- шаги шли отдельными запросами без транзакции, поэтому сбой оставлял данные наполовину стёртыми.

## 2. Машина состояний заявки

```
(нет заявки) ──request──▶ requested ──cancel (дизайнер, до срока)──▶ cancelled
                              │
                              └── purge_after наступил ──▶ expired ──restore (оператор, с причиной)──▶ cancelled
                                                             │
                                          нет hold и архива ─┴─▶ purge_eligible (вычисляется)
                                                                     │
                                                purge (НЕ реализован) ▼
                                                                   purged
```

- `requested`:
  - дизайнер входит, видит проекты, скачивает полный экспорт и может отменить удаление;
  - изменять ничего нельзя: ни проекты, ни ответы, ни КП, ни договоры, ни комнаты;
  - клиенты открывают КП по ссылке, но не могут на них ответить;
  - бриф по ссылке тоже не принимается.
- `purge_after = requested_at + 90 дней`.
- `legal_hold` и `paid_archive_until` — атрибуты заявки. Их ставит оператор через серверную функцию.
  - Legal hold запрещает purge. Отмене он не мешает: отмена сохраняет данные.
  - Платный архив до даты запрещает purge.
- `expired` (DEC-045 (a)) — срок вышел, данные ждут удаления:
  - кабинет закрыт целиком: вместо страниц экран «Аккаунт закрыт» с контактом поддержки; экспорт — 403 `account_closed`;
  - данные по-прежнему только для чтения, КП по ссылке открывается «в архиве»;
  - fail-closed: заявка `requested` с истёкшим сроком везде считается `expired`, даже если перевод статуса
    (`sweep_account_retention_expiry`) ещё не прошёл;
  - оператор (`scripts/account-retention-expiry.ts`): `sweep` — перевод с записью в журнал, `list` — список,
    `restore` — восстановление по просьбе дизайнера, только после срока, с причиной и именем оператора; legal hold не мешает;
  - legal hold и платный архив ставятся и после срока.
- `cancelled` — терминальный статус. Новая заявка — новая строка.
- `purge_eligible` не хранится, а вычисляется: `plan_account_purge` считает его на момент запроса.
- `purged` зарезервирован за будущим разрешённым процессом.

## 2а. Что именно «только для чтения» (после независимого ревью)

При запросе база делает снимок проектов дизайнера (`account_retention_projects`). Дальнейшие проверки опираются на этот снимок, а не на то, что вызывающий видит через RLS. Поэтому проект нельзя вывести из срока, переписав его на другого владельца. Проверяются и старое, и новое состояние строки.

Запись API-ролей (дизайнер, участники студии, публичные ссылки, серверные маршруты) запрещена в таблицах:
- `projects`, `proposals`, `answers`, `risk_cards`, `contract_documents`;
- комнаты: `project_rooms`, `project_participants`, `project_tasks`, `project_task_events`;
- планировки: `layout_documents`, `layout_checkpoints`;
- профиль и события: `designers`, `studio_members`, `events`.

ProjectCEO и интеграции пишут через SECURITY DEFINER-функции. Поэтому запрет стоит на их журналах команд: `project_intelligence.command_records`, `projectceo_product.command_records`, `remhaos_integration.command_records`. Ни одна команда по проекту из снимка не завершается, в том числе команда другого участника проекта.

Сервер приложения закрывает приём брифа, ответ клиента на КП и создание черновика КП до любой записи, включая загрузку файла в хранилище. В кабинете показан баннер «только для чтения».

**Остаётся открытым (известные ограничения):**
- Записи вне журналов команд, например события и очереди моста Telegram, по проекту в сроке не запрещены. Мост по умолчанию выключен (DEC-044 (c)).
- Загрузка файла плана дизайнером (`authenticated-plan-upload`) записывает объект в хранилище до проверки, а таблицы потом отклоняют запись.
- После 90 дней кабинет закрыт на уровне приложения: `proxy.ts` на каждом запросе к `/dashboard` (включая
  клиентские переходы), layout, экспорт (403; при ошибке чтения статуса — 503, не экспорт). Прочие маршруты
  чтения под сессией дизайнера и прямое чтение через API базы после срока не закрыты: запись запрещена, чтение
  своих данных — нет. Так решено владельцем (DEC-046): чтение в базе не закрывается до решения о purge.
- Журнал заявки в экспорт не входит. Статус заявки входит.

## 3. Scope purge (для будущего процесса; сейчас только dry-run)

`plan_account_purge(designer_id)` возвращает без изменений данных:
- **блокеры:** срок не вышел, legal hold, платный архив, нет активной заявки;
- **счётчики:** проекты, КП, ответы, риски, комнаты, версии паспорта, договоры;
- **префиксы хранилища:** `client-uploads/{projectId}/`, `client-uploads/designer-plans/{projectId}/` и файлы договоров.

Будущий purge обязан:
1. Выполняться одной серверной транзакцией на проект. Повтор после сбоя продолжает с того же места (идемпотентность по `case_id` + проект). Каждый шаг записывается в `account_retention_events`.
2. Удалять версии паспорта через отдельную защищённую дверь с журналом. Сейчас триггер неизменяемости запрещает это всем, и это правильно: обойти его можно только осознанным решением.
3. Для проектов, подключённых к ProjectCEO (`project_workflows` с ON DELETE RESTRICT), не удалять каркас проекта, а обезличивать его. Неизменяемый аудит ProjectCEO хранит только идентификаторы.
4. Перепроверять hold и архив непосредственно перед каждым шагом.
5. Никогда не запускаться автоматически по таймеру без отдельного решения владельца (DEC-041 §2).

## 4. Аудит и идемпотентность

- `account_retention_events` — append-only журнал: `requested`, `replayed`, `cancelled`, `legal_hold_set`, `legal_hold_cleared`, `paid_archive_set`, `purge_planned`, `expired`, `restored`. В каждой записи автор и причина.
- Повторный запрос при активной заявке возвращает ту же заявку, а не создаёт новую.
- Отмена после срока отклоняется с понятной причиной (`ACCOUNT_RETENTION_WINDOW_CLOSED`); после срока аккаунт возвращает только оператор (`restore`).

## 5. Чтение и экспорт

- Полный экспорт (`/api/account/export`) доступен дизайнеру всегда, а не только в срок. Он читает постранично под RLS самого дизайнера, а версии паспорта получает через `export_passport_revisions()`. В нём:
  - проекты без токенов доступа;
  - ответы брифа, риски;
  - все версии паспорта;
  - КП без публичной ссылки;
  - метаданные договоров и события;
  - комнаты, участники (без ссылок доступа), задачи;
  - планировки;
  - команда студии.
- Данные ProjectCEO в этот экспорт не входят.
- Файлы в экспорт пока не входят: экспорт перечисляет только их пути. Архив файлов — отдельная задача.

## 6. Что сознательно не сделано

- Нет purge-процесса и нет автоматического удаления по сроку.
- Нет интерфейса оператора для legal hold: есть только серверная функция с правом `service_role`.
- Уже удалённые до этого изменения данные не восстанавливаются. Задним числом ничего не удаляется.
