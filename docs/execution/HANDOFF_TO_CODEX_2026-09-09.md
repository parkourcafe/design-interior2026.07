## 0. Почему этот документ существует и почему не Claude Code Remote

Программа (аудит → дорожная карта → генеральное ТЗ → 30 пакетов работ) была спроектирована для
оркестратора на Claude Code Remote: постоянная сессия, будимая по расписанию, создающая дочерние
рабочие сессии через `create_session`. Это упёрлось в системное ограничение платформы: дочерняя сессия
не может получить более permissive режим прав (`auto`), чем сессия, которая её создаёт, а создающая
(родительская, диалоговая) сессия владельца была в режиме `plan`. Первая попытка оркестратора была
создана без явного `auto`, унаследовала обычный режим — и застряла на 9 часов, ожидая подтверждений,
которые некому было дать (будильник без зрителя). Вторая попытка с явным `auto` отклонена системой
напрямую: `permission_mode 'auto' requires the parent session to be in auto mode (parent is "plan")`.

**Решение владельца:** не бороться с этим ограничением, а перенести исполнение на Codex. Все
продуктовые документы (контракт, каталог пакетов, протокол, карточки) написаны инструментально
нейтрально — они говорят о «рабочей сессии на своей ветке», а не о конкретном API. Единственный файл,
завязанный на инструменты Claude Code Remote, — `docs/execution/ORCHESTRATOR.md`; в разделе 6 ниже
дана его замена.

Если позже владелец переключит режим родительской сессии Claude Code на `auto`/`bypassPermissions`,
механизм Claude Code Remote можно оживить — он не сломан концептуально, просто был заблокирован правами.
Это не приоритет сейчас.

## 4. Определение «сделано» (Definition of Done)

Из мастер-ТЗ §11, продублировано здесь как самое важное:

Каждый пакет — своя ветка `wp/WP-xx-<slug>` от свежего `main`, один PR, только файлы из allowlist
карточки. Перед push — `npm run release:check` обязательно; `test:db4`/`test:db5` локально, если задет
SQL. Обязательные проверки CI на PR: `lint / typecheck / test / build`, `DB4 on postgres:16-alpine`,
`DB4 on postgres:17-alpine`, `DB5 on postgres:16-alpine`, `DB5 on postgres:17-alpine`,
`AP5 authenticated browser matrix`. Evidence-файл `docs/audits/wp/WP-xx_EVIDENCE.md` по шаблону.
Миграции — только additive, одна в работе одновременно (серия S-MIG), ledger трогает только держатель
серии. Слепое ревью (отдельная read-only сессия/прогон, без доступа к транскрипту исполнителя)
обязательно для WP с миграцией, security, CI, каноном — список в §11 мастер-ТЗ. Production, `release`,
Supabase, Railway, второй аккаунт — никто из рабочих пакетов не трогает никогда.

## 6. Как это ведётся без Claude Code Remote — операционная модель для Codex

`docs/execution/ORCHESTRATOR.md` написан под API Claude Code Remote (`create_session`, `send_later`,
`fire_trigger`, Google Drive heartbeat, Notion). Ниже — эквивалент на обычных примитивах git/GitHub,
которые доступны любому агенту с доступом к репозиторию.

**Роль «интегратор» (ты, эта сессия Codex).** На каждом заходе:
1. Прочитать `docs/execution/STATUS.md` и `docs/execution/OWNER_QUEUE.md` — что в работе, что ждёт
   владельца, какие серии заняты.
2. Проверить открытые PR программы (`gh pr list` или эквивалент): для каждого — статус CI. Красный —
   решить: инфраструктурная нестабильность (один повторный прогон) или продуктовая ошибка (чинить в той
   же ветке). Зелёный без открытых замечаний ревью — слить по полномочиям ниже.
3. **Правило слияния (без исключений):** docs-only и не-миграционные PR без метки security при зелёном
   CI и чистом ревью — сливаешь сам. PR с миграцией, RLS, грантами, security-веткой, `.github/workflows`,
   флагами — оставляешь `READY_FOR_OWNER_MERGE`, слияние делает владелец лично.
4. Взять следующий пакет (или несколько параллельно — Codex сам решает, сколько параллельных запусков
   тянуть; ограничение по деньгам см. §7, не по числу сессий как было у Claude Code Remote) из открытых к
   запуску (§5 выше / доска), проверить, что серия свободна, начать работу по карточке
   `docs/execution/wp/WP-xx-*.md` и протоколу `docs/audits/wp/WP_PROTOCOL.md`.
5. Обновить `docs/execution/STATUS.md` (одна строка на пакет: статус, ветка, PR, блокер, дата) и
   `docs/execution/OWNER_QUEUE.md` (новые пункты, отметки о закрытых). Коммит — в отдельную ветку
   `wp/orchestrator-status`, PR docs-only, слить самому же по правилу выше.
6. Одна строка ответа владельцу: что слито, что в работе, что ждёт решения (номера Р), расход.

**Параллельность.** Если Codex поддерживает несколько одновременных запусков (несколько терминалов,
несколько worktree, облачные параллельные задачи) — используй это вместо создания «дочерних сессий»:
каждый параллельный запуск = один пакет = одна ветка = один PR, по тому же протоколу. Единственное
жёсткое ограничение — серийные группы (§8 мастер-ТЗ): миграции, `ci.yml`, командная шина и т.д. держит
только один активный запуск одновременно, остальные ждут его PR.

**Ревью.** Слепое ревью для миграций/security/CI/канона — отдельный запуск (свой terminal/worktree),
который читает только diff PR + evidence-файл + карточку WP, без доступа к истории исполнителя, и
оставляет вердикт `BLOCKER`/`MAJOR`/`MINOR`/чисто. Это то же самое, что уже несколько раз делали сессии
`chatgpt-codex-connector` и Claude Code Review на PR этого репозитория — образец есть в истории PR #124,
#125.

**Heartbeat / надзор.** Необязателен для Codex — вместо него владелец смотрит `STATUS.md` напрямую.
Если хочешь оставить след для существующего сторожа Loops HQ (`watchdog-loop` в Notion), можно продолжать
класть файл `YYYY-MM-DD-remhaos-orchestrator-loop-ok.md` в папку Google Drive
`1fdXopUtFtTkSxg3Qyp0tvSKwPnDT3dHA`, если у этой сессии Codex есть туда доступ; если нет — не обходить
другими способами, просто не вести эту конкретную запись.
